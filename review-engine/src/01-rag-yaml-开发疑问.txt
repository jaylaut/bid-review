rag.yaml:
    rag.yaml 里的数值，大部分是 RAG 领域的最佳实践"基线默认值"，不是从数学公式推导出来的硬真理。
    R0 文档自己写了两句话点明这点：
        ①"阈值全部进配置，不散落在代码里——R7 的阈值标定要改的就是这个文件"；
        ②refusal_threshold: 0.15 # R7 标定，不是拍的。意思是：这些值是先用经验/文献给一个合理起点，等 R7 用真实标书数据做实验（召回率/精确率/F1 扫描）时才最终敲定。

    1.router: {scanned_threshold" 0.05}            # 扫描件判断阈值，> 0.05 判定为扫描件 --  什么大于0.05？依据是什么
    解答：这是 R1 解析路由的探针阈值。一份投标文件（PDF）有两种来源：
        原生文本 PDF（有文字层，可直接复制文字）；扫描件（本质是图片，没有文字层，必须靠 OCR/视觉模型识别）。
        R1 的探针会估算文档里被判定为"扫描图片"的内容占比（比如按页：扫描页 / 总页数，或按区域）。
        当这个扫描占比 > 0.05（即超过 5%）时，就认为"这份文档基本是扫描件"，路由到 mineru-vlm（带视觉能力的解析后端，能 OCR）；否则走默认的 mineru（轻量、快，只处理文字层）。
        依据：5% 是个保守的小阈值——只要文档里有哪怕一小部分扫描页，纯文字解析后端就会在那几页上"丢字"，下游检索直接缺数据。
        设小一点能尽可能避免把"含扫描页的文档"误送进快速通道；但也不能设成 0（否则任何一页扫描就走慢通道，浪费算力）。
        精确的取值口径（按页还是按面积）由 R1 定义，R7 可微调。

    2.dedupe: {exact: true, near: {method: minhash,threshold: 0.85}}  # 精确度取重开-什么意思，近似去重用minhash-什么意思,相似度 > 0.85 去重 -- 0.85的依据是什么？
    解答：(1) exact: true（精确去重开）：完全相同的块只保留一个。判定方法是算文本哈希（如 SHA256），两个块正文一字不差就删冗余。
            标书里常有重复出现的页眉/页脚、标准条款模板，精确去重能去掉这类"复制粘贴"噪音，省索引空间。

        (2) near（近似去重）用 MinHash："近似"指内容高度相似但不完全相同的块（比如同一段要求出现在不同章节、只差几个字）。
            MinHash 是一种用很少计算量估算两篇文章相似度（Jaccard 相似系数）的算法——它把文本切成词袋/ shingles，用一组哈希函数压缩成签名，签名重合度≈真实相似度，不必逐字比对。
            threshold: 0.85（相似度 > 0.85 才去重）：两条线。0.85 是"几乎一模一样"的门槛——高于它才当重复删掉。
        依据：太低（如 0.5）会把"只是有点像但语义不同"的块误删，丢信息；太高（如 0.99）又会放过多余副本，白占索引、还会在检索时让同一内容霸榜。
            0.85 是近似去重的常用保守默认值，平衡"去噪音"和"保信息"，由 R7 按实际重复率微调。

    3.strategy: structural_recursive               # 分块策略：结构化递归 -- 详细介绍什么是结构化递归
    解答：分块（chunking）就是把长文档切成检索用的小段。结构化递归= 两层策略叠加：
        结构化（structural）：先按文档的逻辑结构切——用解析器（mineru）给出的章节树（section_path、标题、表格、列表边界）来切。好处是"一个评分要求/一个条款"尽量完整落在一个块里，不被盲切。
        递归（recursive）：如果某个结构单元（比如一整节）还是太长超过 max_tokens，就按越来越细的分隔符递归下刀：段落 → 句子 → 字符，直到每段都 ≤ 上限。
        递归保证"先在大边界切，切不动了再切小的"，尽量不把一句话从中间劈开。

        对比：固定长度分块（每 512 token 硬切）会粗暴打断语义；纯语义分块（用模型判断）成本高。结构化递归是"尊重文档层级 + 控尺寸"的折中，最适合标书这种层级清晰、条款独立的文档。

    4.max_tokens: 512                              # 子块最大token数 --  为什么是512，依据是什么？
    解答：这是子块（被嵌入、被检索的那段）的最大长度。
    依据：嵌入模型的"黄金窗口"：嵌入模型对"一段只讲一件事"的文本表示最准。块太大（混了多个主题），向量就被平均化、变模糊；块太小（半句话）又缺上下文。
    512 token 是业界最常验证的甜点（256–512 区间），既能装下"一个条款+少量上下文"，又不稀释语义。
    中文换算：Qwen3-Embedding 对中文约 1 token≈1–1.5 字（视分词），512 token≈ 500–700 字，正好是一段评标条款的量级。
    它也是很多嵌入模型训练/评测的默认窗口。最终值 R2/R7 会用真实条款长度分布校准。

    5.overlap_tokens: 64                           # 块之间重叠token数，保证上限连续 --为什么是64，依据是什么？ 如果连续完整的中文语义不等于64，会如何处理？
    解答：重叠指：切长单元时，第 N 块的尾巴和第 N+1 块的开头重复 64 token，作为"缓冲带"，防止一个完整的句子/要求恰好被切在边界上、两半都残缺。
    依据：重叠一般取块尺寸的 10%–15%，64 / 512 ≈ 12.5%，落在典型区间。太小（如 16）挡不住边界切断；太大（如 200）会造成大量冗余、索引膨胀、成本上升。
    “连续完整的中文语义不等于 64，会如何处理？”  —— 这是关键问题，答案是：固定重叠本身不保证语义完整。它只是个"安全垫"。真正保证语义的是上面的递归切分优先在自然边界（句末/段末）下刀；
    切完之后才补 64 token 重叠。所以理想情况是"先在句子边界断开，再叠 64 当保险"。但极端情况下（比如某个超长无标点段落 > 512 token），仍会被硬切——这时靠父子块设计（见第 6 点）
    兜底：子块被切了，但检索命中后会把父块（2000 token）一起返回给大模型看，保证上下文连贯。

    6.parent_max_tokens: 2000                      # 父块最大token数 -- 为什么是2000，依据是什么？ 块是否过大导致向量时，范围太宽泛？
    解答：这是 父子块（parent-child）设计：每个 ≤512 的子块，隶属于一个 ≤2000 的父块（包含子块及其周边上下文）。
    检索/向量用的是子块（512）：向量聚焦、准。
    返回给大模型用的是父块（2000）：当子块命中，把整个父块（或父子一起）喂给下游大模型做判定，让它看到"来龙去脉"。
    你担心的"父块太大、向量范围宽泛"——正好不会发生，因为父块不参与向量检索，它只是"命中后附带的阅读上下文"。向量永远是 512 的子块，不会变宽泛。
    2000 的依据：约为子块的 4 倍，足够包住"一整节"给模型当背景，又不至于把无关内容塞爆上下文。它和 context_budget_tokens: 6000 配合（6000 / 2000 ≈ 最多 3 个父块），保证预算内装得下。

    7.hnsw: { m: 16, ef_construction: 200, ef_search: 128 }     # HNSW 参数 -- HNSW是什么意思？后面的参数分别是什么意思？取值的依据是什么？
    解答：HNSW = Hierarchical Navigable Small World（分层可导航小世界图），是一种向量近似最近邻（ANN）索引。
    没有它，每次查询都要和全表所有向量算一遍相似度（全表扫，慢 100 倍且不报错——这就是 R0 自检第 4 项要拦的）。HNSW 把向量建成"多层图"，查询时从粗到精地"导航"到最近的几个，速度极快。
    三个参数：
        m: 16：图里每个节点最多连几条边（邻居数）。越大召回越高但越占内存。16 是 pgvector 的默认推荐值。
        ef_construction: 200：建索引时插入每个节点要考虑多少候选邻居。越大索引质量越好但建得越慢。200 是"高质量建索引"的常用值。
        ef_search: 128：查询时动态候选列表大小。越大召回越高但查得越慢，可在查询时单独 SET hnsw.ef_search = 128 调整。128 是质量/速度的折中。
    依据：都是 pgvector 官方推荐的"召回/速度/内存平衡"默认值；实际可随数据量和延迟要求微调（召回不够就调大 ef_search，内存紧就调小 m）。

    8.reconcile: { cron: "0 3 * * *", alert_threshold: 0.001 }  # 每天 3 点核对；差异>0.1% 告警 -- 这行配置什么意思？
    解答：reconcile = 对账/核对。这是一个定时任务配置：
    cron: "0 3 * * *"：每天凌晨 3 点跑一次（选凌晨是避开业务高峰）。
    它干什么：把"向量索引/chunks 表"和"权威真相（documents 表 / 原始解析结果）"比对，查出不一致——比如 R0 文档里说的那个真实坑：文档 status='indexed' 了，
    但 chunks 里其实 0 条（写入中途崩了）；或者孤儿块、缺向量的块。
    alert_threshold: 0.001（0.1%）：当异常记录占比 > 0.1% 才告警。低于它视为可自愈的偶发噪音，不报警；超过说明"系统性出问题了"（比如某次入库任务挂了），立刻通知人。
    依据：凌晨低峰跑避免影响线上；0.1% 阈值既能在系统性故障时报警，又不会被个别偶发脏数据淹没告警。

    9.dense_k: 60                           # 向量路召回数量 -- 为什么是60，依据是什么？
    10.sparse_k: 60                          # 全文路召回数量 -- 为什么是60，依据是什么？
    9、10 解答：dense（稠密/向量路）：用嵌入向量做语义检索，按内积相似度取前 60。
        sparse（稀疏/全文路）：用 tsvector 做关键词检索（BM25 类），按文本匹配取前 60。
        为什么都是 60：你最终只要 5 条（top_n），但先多召回再精选是标准做法——
            ①两路要融合，得各给一个候选池；
            ②重排（rerank）需要更大的候选集才能从里面挑出真正最好的 5 条。
        60 是"候选池够大不漏检、又不至于让重排太慢/太贵"的经验值（文献常用 20–100）。两路对称设 60，是为了融合时两路贡献均衡。最终由 R7 按"漏检率"校准。

    11. fuse: { method: rrf, k: 60, pool: 100 } # 融合方法 RRF，常量 k=60，候选池 100 -- 什么是融合方法，RRF是什么意思？常量 k=60，候选池 100 这两个参数具体什么意思？值的依据分别是什么
    解答：融合（fusion）：把"向量路"和"全文路"两份结果合成一份排序。两路互补——语义检索能找"意思相关但用词不同"的，关键词检索能精准命中型号/标准号（见第 12 点）。
    RRF = Reciprocal Rank Fusion（倒数排名融合）。公式：某文档得分 = Σ 1/(k + rank_i)，把它在各路里的排名取倒数相加。
        关键优点：它只用"名次"不用"分数"——因为向量分和全文分量纲完全不同，不能直接相加；但名次可以直接融合。
    k: 60：RRF 的阻尼常数。越大，排名靠前的优势被削弱（更"平均主义"）；越小，第 1 名越压倒一切。论文实证 k=60 在多种数据集上都稳，是经典默认值。
    pool: 100：融合后的候选池上限。dense_k 60 + sparse_k 60 最多 120 条，去重后封顶 100 条进入下一步重排。
    依据：k=60 来自 RRF 原始论文的跨数据集实验；pool=100 在"覆盖度"和"重排成本"间取平衡。

    12.sparse_weight: 1.0                    # 稀疏路权重；型号漏检时升 1.2（R7 实验）-- 这行配置什么意思？
    解答：虽然纯 RRF 本不看分数，但这项配置允许你给稀疏路加权。默认 1.0 = 两路等权。
    “型号漏检时升 1.2” ：R7 单变量实验发现，遇到型号/规格类查询（如"达梦 DM8""H3C S5130"）时，向量语义检索会漏——因为型号是"字面字符串"，不是"语义"，
    向量检索对字面匹配天然偏弱。这时把 sparse_weight 提到 1.2，让关键词路在融合里更占优，就能补上型号漏检。所以它本质是个按查询类型切换的旋钮：普通语义查询用 1.0，型号/标准号密集的查询用 1.2。

    13.candidates: 20                        # 进入重排的候选数 -- 重排是什么意思？选择20的依据是什么？
    解答：重排（rerank）：前面向量检索是"双塔/bi-encoder"——查询和文档各自独立编码再比相似度，快但不准。
    重排换用交叉编码器（cross-encoder，这里用 Qwen3-Reranker）：把"查询+文档"拼在一起送进模型做交叉注意力，直接输出"这条和查询有多相关"的精准分数。所以它比检索准得多，但也慢且贵（要逐对处理）。
    漏斗到这里：融合出的 ~100 条 → 取前 20 条送重排器。
    为什么 20：重排逐对计算，候选太多延迟/成本暴涨；太少（如 5）又可能在重排前就把"真正最相关那条"误删了。20 是"能挑出最佳 5 条、又不至于太慢"的常见默认值（文献多用 20–50）。

    14.top_n: 5                              # 重排后保留数   -- 选择5的依据是什么？
    解答：重排完 20 条，只留最相关的 5 条喂给下游大模型（做评分项判定/生成答案）。
    依据：5 条足够让模型拿到回答一个评分项所需的证据，又不至于用无关内容淹没模型、徒增 token 成本。太少（1–2）容易漏掉关键证据；太多（10+）引入噪音且超预算。
    另外它和 context_budget_tokens: 6000 自洽：5 条子块（~512×5）或少量父块都能轻松塞进 6000 预算。

    15.refusal_threshold: 0.15              # 拒答阈值，R7 标定（非拍脑袋） -- 这行配置什么意思？
    解答：重排器输出一个 0–1 的连续相关分数（靠 R0 自检第 7 项探的 logprobs 还原出来）。如果最相关那条的分数 < 0.15，系统就拒答/标记低置信，而不是硬编一个答案——防止"检索不到相关内容却瞎答"的幻觉。
    R7 标定，不是拍的：这 0.15 是 R7 在真实标注数据上扫不同阈值、看精确率/召回率/F1 选出来的，不是随手写的。
    它和自检第 7 项强相关：如果 logprobs 拿不到，这个分数就永远算不出，阈值永远不触发（静默失效）——这正是 R0 要把它钉进启动自检的原因。

    16.fallback: cloud_then_rrf              # 本地重排失败兜底：先云端，再退回 RRF  -- 这行配置什么意思？
    解答：本地重排器（Ollama 上的 Qwen3-Reranker）万一挂了/超时/OOM，不能让整个检索报错。兜底策略 cloud_then_rrf = 两步降级：
    先尝试云端重排服务（托管的重排 API）；
    云端也失败，就退回融合阶段的 RRF 排名（直接拿融合后的前 5，跳过重排）。
    结果：系统永远能返回一个结果——哪怕质量降级（没重排），也比"直接报错、整个评标卡住"强。

    17.context_budget_tokens: 6000           # 上下文 token 预算  -- 这个token是调远程大模型的token吗？设置6000的依据是什么？
    解答：是的。这是拼装后喂给下游大模型（做判定的 Agent）的上下文 token 总预算——它限制"检索回来的块内容"在组装进 prompt 时最多占 6000 token。
    依据：要够装下 5 条证据（配合 top_n: 5 和父子块），又不至于把模型上下文撑爆。
        给 prompt 本身和模型输出留足空间（主流模型上下文窗口 8K–128K，6000 只占一小块）。
        太大→模型注意力分散、成本涨；太小→证据装不下。具体数随你用的下游模型窗口而定，R7 可调。

    18.order: u_shape                         # 拼接顺序：U 型（相关块优先） -- 这行配置什么意思？
    解答：决定 5 条块在上下文里怎么排。u_shape（U 型）= 把最相关的块放在上下文的开头和结尾，次相关的放中间。
    为什么：大模型有"中间迷失（lost-in-the-middle）"弱点——对放在上下文首尾的内容注意得最牢，中间容易忽略。
    U 型排序就是把关键证据顶到两端，提升利用率。对应的直白做法叫"按相关度排序（最相关的紧挨 prompt）"，U 型是它针对模型弱点的优化版。

    19.l1_ttl: 24h                           # 一级缓存存活 24 小时  -- 本项目中缓存什么内容？什么场景用一级缓存？一级为什么设置24小时？
    20.l2_ttl: 168h                          # 二级缓存存活 7 天  -- 本项目中缓存什么内容？什么场景用二级缓存？二级为什么设置7天
    21.l3_enabled: true                      # 三级缓存开关  -- 什么时候用三级缓存？
    解答（19/20/21）:缓存的内容通常是检索链路的"贵操作结果"：最典型是 (查询 + 项目 + 权限) 对应的"最终检索+重排结果"，或查询向量 embedding（避免重复嵌入相同问题）。命中缓存就能跳过嵌入/检索/重排，直接返回。
    L1（l1_ttl: 24h，一级）：最快、最近（进程内存或本地 Redis）。
        场景：同一天内重复问——比如同一评分项对同一项目被多次评估、用户改个问法重跑。
        为什么 24 小时：标书库一天内基本不变，当天重复（一次评标会话里常发生）能秒回；设 24h 既覆盖当天复用，又会在"夜间库更新"前自然过期，避免长期serve陈旧结果。
    L2（l2_ttl: 168h，二级）：更大更慢一层（持久化 Redis / DB 缓存），7 天。
        场景：跨天/跨周的复用——比如同一套标准评分项在一周内被用到多个不同投标项目。
        为什么 7 天：评标工作常按周展开，一周内复用省算力；比 L1 活得久是因为 L2 存储便宜，且库更新节奏约以周计，7 天后再过期防 stale。
    L3（l3_enabled: true，三级）：最大最冷的一层（可能是语义缓存——按"意思相近"而非精确 key 命中，或分布式/磁盘缓存）。
        什么时候用：L1、L2 都未命中，但你仍想兜住"换了个说法其实问的是同一要求"的查询，或极长尾的复用。开启（true）即启用这最后一道、最省但最慢的防线。
