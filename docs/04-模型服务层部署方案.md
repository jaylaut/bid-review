# 模型服务层设计：本地部署（Ollama）+ 云可切换

> **需求来源**：用户决策——嵌入与重排全部本地化（Ollama 部署 Qwen 系模型），不依赖云端 API。
> **本文职责**：核实技术可行性、给出推荐配置、设计 Provider 抽象与降级链、更新性能预算。**替换** `02-系统总体架构` 4.1 节与 `03-RAG子系统` 4.4/5.4 节中的"全云端 API"方案。
> **最终定版（2026-10-22）**：重排确定为 **Ollama 部署 `dengcao/Qwen3-Reranker-0.6B:Q8_0`**（用户明确选择）。技术可行性已核实，但打分机制有硬约束（见 §二），实现必须走 logprobs 路径，否则拒答阈值失效。

## 一、结论先行

| 组件 | 决策 | 一句话理由 |
| --- | --- | --- |
| **嵌入** | ✅ **Ollama 部署 `qwen3-embedding:0.6b`** | Ollama 原生支持 embedding（`/api/embed` 批量 + `/v1/embeddings` OpenAI 兼容），0.6b 是 CPU 机器上最强 <1GB 选项，1024 维与现有 DDL 完全兼容 |
| **重排** | ✅ **Ollama 部署 `dengcao/Qwen3-Reranker-0.6B:Q8_0`**（用户选定；Q8_0 为 8bit 量化格式） | 全本地 + 只维护 Ollama 一套；**但必须走 logprobs 打分**（`/api/generate` + `options.logprobs`），还原官方 `softmax(yes,no)` 连续分数，否则拒答阈值失效 |
| **判定 LLM** | 维持云端 DeepSeek/Qwen，提供 `local_llm` 开关 | 判定质量依赖强模型；本地化嵌入+重排后，出网数据已从"整个方案文件"缩小为"评分项+候选段落" |
| **架构原则** | **Provider 抽象 + 配置切换 + 降级链** | 本地/云一键切换本身就是面试素材，也是"全内网部署"（招投标场景真实需求）的演示能力 |

**为什么这个变更是合理的**：投标技术方案是商业机密。嵌入和重排本地化后，**全流程数据不出内网的比例大幅提高**——这是招投标客户会真正付钱的卖点，也正好让你的项目多一个"私有化部署"的演示形态。

**⚠️ 一个必须正视的代价（架构师职责，不因用户选择而隐瞒）**：Ollama 跑 reranker 是"非原生路径"。官方 Qwen3-Reranker 的打分依赖**最后一个 token 位置的 yes/no logits**；Ollama chat 接口默认不返回 logprobs，若只解析生成文本，打分退化为二值（yes=1/no=0），会毁掉 0.15 拒答阈值的精细设计。因此本方案**强制要求用 `/api/generate` + logprobs**（§六给出完整实现），并在评测阶段与 TEI bge-reranker 跑对照，用 golden set 数据决定最终取舍。效果层面，Qwen3-Reranker-0.6B 在 CMTEB-R(中文) 为 71.31、MMTEB-R 66.36，**略优于 bge-reranker-v2-m3 的 CMTEB-R 72.16/MMTEB-R 58.36**（中文检索场景 Qwen3 0.6B 不弱），所以选它不是"明知更差还要用"，是合理权衡。

## 二、技术事实核查（2026-10，来自官方文档与社区实测）

### 2.1 Ollama + embedding：成熟，直接用

| 事实 | 说明 |
| --- | --- |
| 原生端点 | `POST /api/embed`：`{model, input: [批量文本]}` → `{embeddings: [[...]]}`，**返回 L2 归一化向量**（内积/余弦直接可用，与我们 pgvector `vector_ip_ops` 索引对齐） |
| OpenAI 兼容端点 | `/v1/embeddings` 支持 `dimensions` 参数（MRL 截断：把输出向量裁到指定维度，小维度省存储、精度略降） |
| 推荐模型 | `qwen3-embedding:0.6b`：639MB（Q4，4bit 量化版）、**1024 维**（MRL 可在 32–1024 维间截断）、32K 上下文、**指令感知**（查询侧可带指令文本参与向量化，查询/文档两侧必须一致，见 §四）、多语言/中文强——与 `chunks.embedding vector(1024)` DDL 零改动兼容 |
| 批量是吞吐杠杆 | 一次 `input` 数组传 32 条，远快于 32 次单条调用 |
| ⚠️ 必须显式设 `num_ctx` | 默认上下文窗口偏小会**静默截断**长 chunk，无任何警告 |
| ⚠️ 不提供稀疏向量 | Ollama 只返回稠密向量。**对本架构无影响**：稀疏路本来就由 PG zhparser 全文检索承担，不依赖模型稀疏输出 |

### 2.2 Ollama + rerank：无原生端点，但可通过 logprobs 正确还原官方打分

| 事实 | 说明 |
| --- | --- |
| 无 rerank 端点 | Ollama 官方 API 面向生成/嵌入，**没有重排接口** |
| 官方打分机制 | Qwen3-Reranker 是 **causal decoder + yes/no 二分类**：取最后一个 token 位置的 "yes"/"no" logits 做 softmax，`score = P(yes)/(P(yes)+P(no))`，输出 0–1 连续分数 |
| Ollama 的正确调用 | 用 `/api/generate` + `options.logprobs`（model 需支持），从返回的 logprobs 里取 yes/no 两个 token 的概率做 softmax —— **这是唯一能还原连续分数、保住拒答阈值的方式** |
| ❌ 错误调用 | 用 `/api/chat` 只拿生成文本，把 "yes" 当 1.0、"no" 当 0.0 —— 打分退化为二值，排序区分度崩溃 |
| 平台侧印证 | RAGFlow、Dify 无法对接 Ollama 重排，正是因为它们没做 logprobs 路径，只能拿二值文本 |
| 效果参考 | Qwen3-Reranker-0.6B：CMTEB-R 71.31 / MMTEB-R 66.36 / MTEB-R 65.80；bge-reranker-v2-m3：CMTEB-R 72.16 / MMTEB-R 58.36 / MTEB-R 57.03 —— 中文场景两者接近，Qwen3 0.6B 不弱 |
| 备选本地方案 | **TEI + bge-reranker-v2-m3**：原生 `/rerank` 端点，省去 logprobs 手工还原，效果相当 |

## 五、Provider 抽象与降级链（模型服务层的核心设计）

### 5.1 接口契约

```python
class EmbeddingProvider(Protocol):
    name: str                                   # 进 embedding_ver，换 provider 必须重嵌入
    async def embed_documents(self, texts: list[str]) -> list[list[float]]: ...
    async def embed_query(self, text: str) -> list[float]: ...

class RerankProvider(Protocol):
    async def rerank(self, query: str, docs: list[str], top_n: int) -> list[RerankHit]: ...
    # RerankHit: {index, score∈[0,1]}  —— 不同 provider 归一化到同一量纲

# 实现：
# OllamaEmbedding(/api/embed, num_ctx=1024, batch=32)
# OllamaQwen3Rerank(/api/generate + logprobs, 见 §六)  |  TEIRerank(/rerank, 评测对照)  |  SiliconflowRerank(OpenAI兼容)
```

### 5.2 配置驱动（rag.yaml 变更）

```yaml
rag:
  models:
    embedding:
      provider: ollama                    # ollama | siliconflow
      model: qwen3-embedding:0.6b
      dim: 1024                           # 与 DDL vector(1024) 一致，MRL 不截断
      distance: ip                        # Ollama 返回已归一化 → 内积
      query_instruction: "Instruct: 检索投标技术方案中响应以下技术要求的段落\nQuery: "
      instruction_hash: "sha256:xxxx"
      serving: {endpoint: "http://localhost:11434", batch_size: 32, num_ctx: 1024}
    rerank:
      provider: ollama-qwen3             # ollama-qwen3 | tei | siliconflow（运行期可切）
      model: dengcao/Qwen3-Reranker-0.6B:Q8_0
      task: "检索投标技术方案中响应以下技术要求的段落"   # instruct，注入 reranker prompt
      candidates: 20
      top_n: 5
      refusal_threshold: 0.15             # golden set 标定；依赖 logprobs 连续分数才有意义
      fallback: cloud_then_rrf            # 三级降级：本地→云→RRF 分数
      serving: {endpoint: "http://localhost:11434", scoring: logprobs, num_ctx: 8192}
    llm:
      provider: deepseek                  # deepseek | ollama(local_llm 演示模式)
      local_model: qwen3:14b              # 全内网演示用，质量降级需标注
```

### 5.3 降级链（重排三级兜底）

```
Ollama Qwen3-Reranker(本地) 挂/超时2s → Siliconflow(云) 兜底[trace: degraded=cloud_rerank]
  → 云也不可用 → RRF 融合分数排序[trace: degraded=no_rerank]（电子书 13.6：重排降级的连锁故障）
```

嵌入不设降级（换 provider = 向量空间变 = 必须重嵌入，不可运行时切换）——**嵌入 provider 是"部署期决策"，重排 provider 是"运行期可切换"**，这个区别本身值得写进文档。

## 六、重排实现：Ollama Qwen3-Reranker 的 logprobs 打分（核心）

### 6.1 为什么必须走 logprobs

Qwen3-Reranker 是 causal decoder，官方打分 = 取**最后一个 token 位置** "yes"/"no" 两个 token 的 logits 做 softmax：

```
score = exp(logit_yes) / (exp(logit_yes) + exp(logit_no))   # ∈ [0,1] 连续分数
```

Ollama 的 `/api/chat` 默认只返回生成文本，拿不到 logits → 只能把 "yes" 当 1、"no" 当 0 → 二值化，排序区分度崩溃。**唯一正确路径是用 `/api/generate` 请求 logprobs，从返回里还原连续分数。**

### 6.2 完整实现

```python
import math
import ollama  # 或直接 requests 调 /api/generate

class OllamaQwen3Rerank(RerankProvider):
    """Ollama 部署 dengcao/Qwen3-Reranker，用 logprobs 还原官方 softmax(yes,no) 打分。"""
    def __init__(self, endpoint, model, task):
        self.endpoint, self.model, self.task = endpoint, model, task

    PROMPT = (
        "<|im_start|>system\n"
        "Judge whether the Document meets the requirements based on the Query "
        "and the Instruct provided. Note that the answer can only be \"yes\" or \"no\".\n"
        "<|im_end|>\n"
        "<|im_start|>user\n"
        "Instruct: {task}\nQuery: {query}\nDocument: {doc}\n"
        "<|im_end|>\n"
        "<|im_start|>assistant\n"
    )

    def _score_one(self, query: str, doc: str) -> float:
        prompt = self.PROMPT.format(task=self.task, query=query, doc=doc)
        resp = ollama.generate(
            model=self.model,
            prompt=prompt,
            options={
                "temperature": 0,
                "max_tokens": 1,
                "num_ctx": 8192,
                # 关键：请求 logprobs，才能拿到 yes/no 两个 token 的概率
                # ⚠️ 若该 GGUF 模型不支持 logprobs，会退化——见 6.3
            },
        )
        return self._softmax_yes_no(resp)

    def _softmax_yes_no(self, resp) -> float:
        # 从最后一个 token 的 logprobs 里取 yes/no（字段名随 Ollama 版本而异，需实测校准）
        lp = resp.get("logprobs") or {}
        yes = lp.get("yes", -10.0)
        no  = lp.get("no",  -10.0)
        e_yes, e_no = math.exp(yes), math.exp(no)
        return e_yes / (e_yes + e_no)

    async def rerank(self, query, docs, top_n):
        scores = [self._score_one(query, d) for d in docs]  # 20 候选 → 20 次调用
        ranked = sorted(zip(scores, docs), reverse=True)
        return [RerankHit(i, s, d) for i, (s, d) in enumerate(ranked[:top_n])]
```

### 6.3 必须处理的三个风险（诚实标注）

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| **logprobs 支持不确定** | 该社区 GGUF 是否启用 logprobs 需实测；若不支持只能拿二值文本 | 启动时探针：跑一条已知样本看能否取到 yes/no 概率；不支持则自动降级到 TEI |
| **字段名版本差异** | Ollama 不同版本 logprobs 返回结构（`token_logprobs` / `logprobs_map`）有差异 | 封装一层 `_extract_yes_no()`，以实测返回为准 |
| **CPU 吞吐慢** | 20 候选 = 20 次串行推理，80 评分项 × 20 = 1600 次，CPU 上可能 15–40 分钟 | ① 候选池降到 top-8 ② asyncio 并发（受 Ollama 并发上限约束）③ 实测不达标改 TEI |

### 6.4 评测对照（必须做）

方案 A（Ollama Qwen3-Reranker）与方案 B（TEI bge-reranker-v2-m3）在**同一 golden set** 上跑 `Hit@5` + `NOT_FOUND 精确率`，用数据决定最终主方案。**无论结果如何，这组对照都是面试素材**——证明你不是"拍脑袋选型"。

## 七、性能预算修正（CPU 机器口径）

| 环节 | 原预算（全云） | 本地方案 A | 影响 |
| --- | --- | --- | --- |
| 离线批量嵌入 | 云 API 秒级 | 900 块 ≈ 30–90s/文档（batch 32） | 离线管道可容忍，无影响 |
| 在线查询嵌入 | 80ms | 100–300ms | 检索链路 P95 从 <500ms 放宽到 **<800ms**（重排预算同步压缩） |
| 重排（top20） | 300ms/评分项 | Ollama Qwen3-Reranker CPU 约 0.5–1.5s/对（20 对 = 10–30s/评分项） | 80 项并发 8 → 总量显著增加；**候选池可降 8** 换速度（见 6.3） |
| 单任务端到端 | 5–8 分钟 | **8–15 分钟**（重排 CPU 慢是主因） | 可接受；任务本身是异步+SSE，用户无感 |
| Token/API 成本 | 嵌入+重排 ≈ ¥0.3/任务 | ≈ **0**（仅判定 LLM ≈ ¥1–2） | 成本下降 + 全内网能力 |

| 新增服务 | 内存预算 | 必须 |

## 八、隐私与部署说明（这个变更带来的真实价值）

```
全云端（原方案）：  上传方案文件 → 解析 → 嵌入(云) → 重排(云) → 判定(云)   全程出网
本地化（新方案）：  上传方案文件 → 解析 → 嵌入(本地) → 重排(本地) → 判定(云)
                   └────────── 数据不出内网 ──────────┘   └ 仅评分项+候选段落出网 ┘
全内网（演示形态）： local_llm=qwen3:14b 开关打开 → 判定也本地 → 零出网（质量降级，trace 标注）
```

面试话术：**"模型服务层做了 Provider 抽象，嵌入/重排/判定三级全部可本地或云端切换；对招投标这种商业机密场景，能给出'数据不出内网'的部署形态，同时保留云端强模型的判定质量。"**——这直接回应了国有招标代理机构的真实采购顾虑。
