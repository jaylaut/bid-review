# R7 · 评测、增益实验与阈值标定

上一份：[R6](R6-三级缓存与性能预算.md) · 工期：3 天 · 前置：**golden set 80–120 项已标注**（P0 人工活，全项目最大卡点）

> **当前状态（2026-10-27，以 [11](../11-总体开发路线（RAG+Agent+Java）.md) 为准）**：`eval/golden_set.jsonl` **不存在**，P3 全部数字阻塞。评测跑批入口已提前落地（`agent/eval_runner.py`，A8 交付物，本线直接复用，不另建脚本）。

## 这个阶段只干一件事

让每个组件的增益**可证明**，让每个阈值**有据可查**。

没有这一章，前面六章的所有工作都无法回答两个问题："双路比单路到底好不好？好在哪？"和"拒答阈值为什么是 0.15 不是 0.2？"——面试问到这里，有数据和没数据是两种回答。

## 先解决卡点：golden set

```jsonl
{"item_id": "S3.2.4", "item_text": "支持国产数据库（达梦、人大金仓）适配",
 "category": "技术参数",
 "requirement_must": ["达梦适配", "人大金仓适配"],
 "expected_verdict": "PARTIAL",
 "expected_missing": ["人大金仓适配"],
 "evidence_doc": "投标文件-技术部分.docx", "evidence_page": 87, "evidence_section": "3.2.4"}
```

格式与 A1 共用（同一份文件两个消费者）。三条标注纪律：

- **`expected_verdict` 四种值都要有足够样本**，尤其 `NOT_FOUND`——最容易出错的类别，也是业务上最要命的（漏判放走不合格方案）；
- `evidence_page/section` 是 Hit@5 的标准答案锚点，**用页码不用文本比对**（文本可能被切到相邻块，页码是稳定锚点）；
- 数量少于 80 就别出数字：20 道题差一道就是 5 个点，噪声比信号大，后面所有"提升 3pt"的结论都立不住。

> 标注是全项目唯一的人工密集阶段，越晚开始越晚完工。先标 40 项跑通流程，再补到 120——**不要用假数据出数字**，基线造假比没有基线更糟（11 §四原话）。

## 分层指标：检索和判定分开算

| 指标 | 衡量什么 | 门槛 |
| --- | --- | --- |
| **Hit@5** | 标准答案的证据片段在不在 top5 | ≥ 0.75（P2 硬验收） |
| **Recall@20** | 前 20 条能捞回多少比例的正确证据 | 参考值（衡量召得全不全） |
| 判定准确率 | verdict 判对的比例（4 类混淆矩阵） | 基线 40–65% 起步 |
| **NOT_FOUND 精确率/召回率** | 漏判"未响应"的控制 | 精确率 ≥ 0.9 且漏检率 ≤ 5% |
| Faithfulness | 结论是否被证据支持 | ≥ 0.85 |

**为什么 NOT_FOUND 单独监控**：它错两个方向的代价不对称——漏判（实际没响应却判 PARTIAL）= 放走不合格方案；误判（实际有响应却判 NOT_FOUND）= 冤枉投标方。混在总准确率里，这两类错误会被 PASS 类的高准确率稀释掉。

## 单变量实验：每加一个组件跑一次全量

顺序铁律（03 §九、电子书 21 章）：**每加一个组件就跑一次评测，无增益就回滚**。

按 03 §九的实现顺序，实验计划天然就是一张表：

| 实验 | 变量 | 对照 | 预期（03 口径） |
| --- | --- | --- | --- |
| E1 | 定长切分 → 结构化分块 + 父子块 | 同查询、同参数 | 各项增益 ≥ 3pt |
| E2 | 单路向量 → 双路 + RRF | 同分块、同参数 | 各项增益 ≥ 3pt |
| E3 | 无重排 → Qwen3-Reranker(logprobs) | 同分块、同召回 | 各项增益 ≥ 3pt |

三条执行纪律：

1. **一次只变一个**。同时上"结构化分块 + 双路 + 重排"，Hit@5 涨了 8 个点，你说不清是谁的功劳——三个都留还是砍两个？说不清就都无法决策。
2. **判定逻辑和业务代码共享同一份**。跑批调用的就是链路上的 `retrieve()` / `assemble_context()`，不存在"评测版检索"——评测跑出来的分数等于业务真实水平。跑批入口统一用 `agent/eval_runner.py`，**不另建 `run_eval.py`**（两套脚本必然漂移，漂移的评测数字比没有评测更糟）。
3. **报告带日期 + commit hash**：`eval/reports/YYYY-MM-DD-<commit>.json`。不然跑 20 次互相覆盖，想对比"上周那次改动"时找不到。

**逐项增益表就是面试的核心素材**——"结构化分块 +4.2pt、双路召回 +5.1pt、重排 +3.8pt，每项都有数据和回滚记录"，这句话比任何架构图都有说服力。

## 阈值标定：0.15 是扫出来的，不是拍的

重排拒答阈值 0.15 的标定流程（03 §七）：

```
1. 用 golden set 跑全量，收集每个评分项的重排 top1 分数分布
2. 扫 {0.10, 0.15, 0.20, 0.25} 四个候选阈值
3. 每个阈值算 NOT_FOUND 精确率和漏检率
4. 取"精确率 ≥0.9 且漏检率 ≤5%"的工作点 → 写回 config/rag.yaml
```

两个纪律：

- **在 dev_bucket 上标定，holdout 上验证**。在同一批题上反复调阈值，最后 92% 是"背答案背出来的"（A8 的分桶纪律，RAG 线同样适用）。
- **阈值可以按 category 分桶**（11 §3.4）：资质类评分项的应答模式（一张证书扫描件）和技术参数类（正文大段描述）的分数分布本来就不一样，全局一个阈值必然两头将就。先全局，分布差异显著了再分桶——别一步跨太远。

## 权限越权测试：进 CI，不是进文档

P2 硬验收之一："跨项目检索返回空"。测试形态：

```python
async def test_cross_project_retrieval_returns_empty():
    # 用户 A 的身份查项目 B 的评分项 → 空结果或 PermissionDenied，绝不返回 B 的数据
    ctx_a = AuthContext(user_id="u1", project_id="proj-a", ...)
    q = RetrieveQuery(item_id="x", query_text="...", project_id="proj-b", ...)
    with pytest.raises(PermissionDenied):
        await retrieve(q, ctx_a)
    # 以及：构造合法 project_id 但 doc 属于 proj-b 的库 → SQL 层过滤返回空
```

**为什么进 CI**：权限是"加了就可能被重构掉"的功能——某天有人"优化"SQL 把 `WHERE project_id` 挪进应用层过滤，单测全绿、功能看起来正常，但数据已经出域。CI 门禁是唯一可靠的看守。

## 检索侧 trace 必埋字段

排查"这个评分项为什么判错"时，检索侧要看的东西（A8 字段的子集，检索线补全）：

```
dense_hits / sparse_hits   # 两路各自召回多少。一路掉到 0 = 那路坏了
rerank_top1                # 拒答阈值看的就是它
degraded                   # none | cloud_rerank | no_rerank
cache_hit                  # none | l1 | l2 | l3（R6）
embedding_ver / chunking_ver  # 结论必须能回答"当时用的哪个版本"
```

> 【why】这些字段是按"排查时需要什么"倒推的：判错了 → 看 rerank_top1 和 confidence；变慢了 → 看分段耗时；变贵了 → 看缓存命中；看不出原因 → 看 degraded 是不是走了降级。**少一个字段，排查时就多猜一轮。**

## 本阶段术语

> 【白话】**golden set**：人工标注好"该判成什么、依据在哪页"的标准题集。没有它，一切优化都是拍脑袋。
> 【白话】**单变量实验**：对比实验里只准变一个东西。同时变三个，涨了也说不出是谁的功劳。
> 【白话】**逐项增益表**：每个组件各带来多少提升的记录表。它是"我的优化有效"的唯一证据形态。
> 【白话】**工作点**：阈值标定选中的那个具体数值。"精确率达标前提下的漏检最小点"。
> 【白话】**holdout**：留出集。只在最终验收用的题，平时调参绝不看——看了就等于泄进训练循环。

## 配置参数治理：rag.yaml 三级分类

> 【why】rag.yaml 里的数值，大部分是 RAG 领域的最佳实践"基线默认值"，不是从数学公式推导出来的硬真理。这种"起步用默认值"的做法本身合理（没数据前无法推导最优），但前提是**把它们当假设而非结论**，并用 R0 的 fail-fast 拦住静默错配、用 R7 的真实数据把高风险参数钉死。下面把 21 个被逐项追问的参数（外加 3 个一致性硬约束）明确分级，作为 R7 标定的作业清单。

### 🔴 硬约束（不是默认，是必须一致；错配即 fail-fast，不可当作普通默认值调）

这类参数一旦和下游不一致，不是"效果差"而是"静默出错/全错"，由 R0 七项启动自检兜底，不在 R7 标定范围内，也**不应被随意改成"试试看"的值**：

| 参数 | 一致性要求 | 兜底检查 |
| --- | --- | --- |
| `embedding.dim` (1024) | 必须与 `chunks.embedding` 的 DDL 维度一致 | R0 第 5 项 |
| `embedding.distance` (ip) | 必须与 HNSW 索引算子类 `vector_ip_ops` 一致 | R0 第 4 项（索引存在性；算子需人工核对） |
| `embedding.serving.num_ctx` (≥1024) | 必须 ≥ 最长 chunk 的 token 数，否则长块被静默截断 | R0 第 6 项 |

> 这三项虽不在"21 个追问参数"之列，但同属 rag.yaml，且是其余所有检索参数的前提——前提错了，上层怎么标定都白搭。

### 🟡 必须标定（R7 用真实标注数据定；标书领域高风险，标定为必做）

这类参数依赖真实的"查询分布 × 文档分布"，且出错代价高（漏检一条要求=错误评标结论）。**必须用 golden set 跑单变量实验/扫参确定，不能停留在默认值**：

| # | 参数 | 为什么在本领域必须标定 | R7 怎么定 |
| --- | --- | --- | --- |
| 1 | `parsing.router.scanned_threshold` (0.05) | 扫描件识别错了→整份文档解析丢字→检索永久缺数据 | R1 拿真实混合文档验证召回 |
| 2 | `cleaning.dedupe.near.threshold` (0.85) | 太低误删语义不同的块（丢证据），太高留冗余副本（霸榜/占索引） | 按真实重复率扫 {0.80, 0.85, 0.90} |
| 4 | `chunking.max_tokens` (512) | 中文评标条款常带"主要求+子条件"，512 可能切不断或切太碎 | 用真实条款长度分布验证 |
| 9 | `retrieve.dense_k` (60) | 向量路召回覆盖度，直接影响 Hit@5 | 扫 {30, 60, 100} 看 Hit@5 / Recall@20 |
| 10 | `retrieve.sparse_k` (60) | 全文路召回覆盖度，型号/标准号漏检的关键 | 同上，对称扫参 |
| 12 | `retrieve.sparse_weight` (1.0) | 型号/规格类查询向量路天然偏弱，需加权补漏检 | 针对型号类查询做单变量实验，确认 1.2 生效 |
| 13 | `rerank.candidates` (20) | 进入重排的候选数，太少可能漏掉最相关条，太多延迟/成本暴涨 | 扫 {10, 20, 50} 看判定准确率 |
| 14 | `rerank.top_n` (5) | 喂给下游模型的证据条数，影响 Faithfulness 与成本 | 结合 `context_budget_tokens` 验证 |
| 15 | `rerank.refusal_threshold` (0.15) | 漏判/误判代价不对称（放走不合格 vs 冤枉投标方） | 已有标定流程（扫 0.10/0.15/0.20/0.25，按 category 分桶） |
| 17 | `assemble.context_budget_tokens` (6000) | 依赖下游模型窗口，太小装不下证据、太大分散注意力 | 按实际模型窗口与 top_n 验证 |

> 标书评标的"高后果"属性，把这一类从"可选项"变成"必做项"。尤其 `refusal_threshold` 必须按 category 分桶（资质类 vs 技术参数类分数分布不同），且遵守 dev_bucket 标定、holdout 验证的纪律。

### 🟢 稳健默认（文献/社区反复验证，基本可信，低优先级微调）

这类参数有扎实的文献或工程依据，风险低，可在 R7 跑批时顺带观察、不必优先投入：

| # | 参数 | 依据 | 微调方向 |
| --- | --- | --- | --- |
| 3 | `chunking.strategy` (structural_recursive) | E1 单变量实验已验证优于定长切分（+≥3pt） | 设计选择，非纯默认，已锁定 |
| 5 | `chunking.overlap_tokens` (64) | ≈12.5% 块长，文献推荐的 10–15% 区间 | 随 max_tokens 等比调整 |
| 6 | `chunking.parent_max_tokens` (2000) | ≈4× 子块，足够包住一整节背景 | 随下游窗口调整 |
| 7 | `indexing.hnsw` (m=16, ef_construction=200, ef_search=128) | pgvector 官方推荐平衡点 | ef_search 可按延迟/召回微调 |
| 8 | `indexing.reconcile` (cron 3点, alert 0.001) | 低峰窗口 + 0.1% 系统性故障阈值 | 运维约定，按业务节奏调整 |
| 11 | `retrieve.fuse` (rrf, k=60, pool=100) | RRF k=60 跨数据集实证稳；pool 平衡覆盖/成本 | pool 可随 k 调整 |
| 16 | `rerank.fallback` (cloud_then_rrf) | 工程降级策略，保证不报错 | 策略选择，非数值调优 |
| 18 | `assemble.order` (u_shape) | 缓解 LLM"中间迷失"，首尾注意力最强 | 实验验证类，低风险 |
| 19 | `cache.l1_ttl` (24h) | 当天评标会话复用，夜间库更新前自然过期 | 按数据更新频率调整 |
| 20 | `cache.l2_ttl` (168h) | 跨周复用，存储便宜 | 同上 |
| 21 | `cache.l3_enabled` (true) | 最冷一层语义/长尾兜底 | 开关类，观察命中率再定 |

### 治理纪律

- **🟡 类必须进 R7 标定计划表**：每个参数写明"扫哪些候选值、看哪个指标、工作点怎么选"，git log 留标定提交。
- **🔴 类进 R0 自检**：任何改动触发自检，不允许绕过。
- **🟢 类允许"先信默认值、跑批时顺带观察"**，但 E1/E2/E3 实验报告里要注明这些参数取值，保证可复现。
- 一句话：**默认值是起点不是终点；🔴 靠自检兜底、🟡 靠数据标定、🟢 靠文献信任——三者共同让 rag.yaml 从"合理猜测"变成"有据可查"。**

## 完成标准

- golden set ≥ 80 项（含 dev_bucket / holdout 分桶），标注规范可复述
- E1/E2/E3 三个单变量实验跑完，逐项增益表落盘，每项有数据和"留/滚"决策
- 拒答阈值完成标定，`config/rag.yaml` 的 `refusal_threshold` 是从扫参结果写回的值（git log 能看到标定提交）
- 越权测试进 CI：人为把 `WHERE project_id` 挪出 SQL，门禁报错
- 一条命令出全量报告（复用 `agent/eval_runner.py`），文件名带日期 + commit
- rag.yaml 参数完成三级分类（🔴/🟡/🟢），🟡 类标定为必做项且 git log 有标定提交（见上文"配置参数治理"）

## RAG 线到此收口

R0 契约 → R1 解析清洗 → R2 分块 → R3 入库 → R4 召回 → R5 重排组装 → R6 缓存 → R7 评测。顺序逻辑：**每一步都在为下一步提供判断依据**（R2 的块质量决定 R4 的召回上限，R5 的分数分布决定 R7 的阈值，R7 的增益表决定前面哪些设计值得留）。
