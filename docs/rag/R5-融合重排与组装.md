## 这个阶段只干一件事

三个环节各自解决一个问题：融合解决"两路怎么合"、重排解决"100 选 5 选谁"、组装解决"喂进去的顺序和形态"。

## RRF 融合：只用名次，不用分数

```python
# score = Σ 1/(k + rank_i)，k=60
def rrf_fuse(dense, sparse, *, k=K, pool=POOL) -> list[Candidate]:
    for rank, c in enumerate(dense, start=1):
        scores[c.chunk_id] = scores.get(c.chunk_id, 0.0) + 1.0 / (k + rank)
        c.dense_rank = rank
    for rank, c in enumerate(sparse, start=1):
        scores[c.chunk_id] = scores.get(c.chunk_id, 0.0) + 1.0 / (k + rank)
        c.sparse_rank = rank
    ...
```

三条原理：

- **为什么只用名次**：两路分数量纲不同（内积 vs ts_rank_cd），直接比分数是错的——向量路 0.82 和全文路 0.31 没有可比性。RRF 的全部意义就是**把两路都换成"第几名"这个统一量纲**。
- **为什么两路都命中的天然被提升**：Σ 1/(60+rank) 对双命中 chunk 是两项相加，单命中只有一项。"向量觉得相关 + 字面精确匹配"的段落正是要找的应答位置——RRF 不需要显式设计这个偏好，数学上天然如此。
- **k=60 是平滑常数**：rank 1 → 1/61 ≈ 0.0164，名次差距被压缩。k 太小则第 1 名通吃，双路互补性浪费；k 太大名次几乎无差异。60 是经典常数（电子书 12.2），本项目无脑沿用。

**`sparse_weight` 预留**：RRF 天然两路平权，已够用；若 R7 评测发现型号类评分项漏检，再上"稀疏路加权 1.2x"——**单变量实验验证后再开**，配置里已经有这个字段（R0），默认 1.0。

## 重排：logprobs 还原连续分数

Qwen3-Reranker 是 **yes/no 二分类 decoder**——它回答的问题是"这段文档响应这个查询吗？是/否"。

```python
def yes_no_probability(logprob_entries: list[dict]) -> float:
    """从首个 token 的 top_logprobs 还原 P(yes)。返回 0-1 连续分数。"""
    top = (logprob_entries[0].get("top_logprobs") if logprob_entries else []) or []
    scores = {str(e.get("token", "")).strip().lower(): float(e.get("logprob", 0.0)) for e in top}
    if "yes" not in scores or "no" not in scores:
        raise ValueError(...)   # 见下方【坑】
    p_yes, p_no = math.exp(scores["yes"]), math.exp(scores["no"])
    return p_yes / (p_yes + p_no + 1e-12)
```

### 为什么必须 logprobs，不能用 chat 拿文本

```
chat 路线：问它"相关吗" → 它答"是" → 映射成 1.0         ← 二值，阈值 0.15 永远不触发
logprobs 路线：取 yes/no 的 logprob → softmax → 0.73    ← 连续，阈值才有意义
```

R0 说的"拒答阈值 0.15"依赖的是**连续分数**。用 chat 文本二值化，所有分数只有 0 和 1，"top1 < 0.15 判 NOT_FOUND"这条路径直接死掉——而"拒答即结论"是本项目的核心语义（03 §一）。这也是 R0 自检第 7 项存在的原因：**logprobs 探针不过，后面全白干**。

> 【坑】`yes`/`no` 不在 top_logprobs 时**抛错，绝不猜一个默认分**：猜的分数会污染拒答阈值——一个编造的 0.5 会让本该 NOT_FOUND 的评分项判成 PARTIAL。宁可降级，也要干净的分数。

### 三级降级链

```
Ollama Qwen3-Reranker(本地) 挂/超时 2s → 云 API 兜底（degraded=cloud_rerank）
                                  ↓ 未配置/也挂
                          RRF 融合分数排序（degraded=no_rerank）
```

- 单对超时 2s：重排是延迟敏感环节，挂了就走降级，**不硬等**——本地 CPU 重排 20 候选要 10–30s，等满超时整个任务都超时了。
- 降级不是静默的：返回 `degraded` 标记，A8 的 trace 必须记录。**静默降级 = 质量滑坡看不见**——你以为在用重排，其实 RRF 分数排在顶上，Hit@5 掉了都没人知道。
- 当前实际只走了两级（云 API 未配置）：本地→RRF。配置好云 API 后中间一档才生效。

### 重排分数的三个二次用途

1. **拒答路径**：top1 < 0.15 → 触发"未响应"判定（`NOT_FOUND` 是合法判定结果，进偏离表——**漏判比误判更严重，单独监控**）
2. **confidence 的组成分量**：A6 置信度计算的输入之一
3. **trace 标定**：写进 trace，R7 的阈值标定就扫这批数据

阈值 0.15 **不是拍的**，是 golden set 上扫 {0.10, 0.15, 0.20, 0.25} 标定出来的工作点（R7 有流程）。标定前它就是配置里的一个默认值，别当真理。

## 上下文组装：父块回溯 + U 型 + 预算

```python
async def assemble_context(hits, *, parent_lookup=None, budget_tokens=6000) -> list[EvidenceBlock]:
    blocks = []
    seen_parents: set[str] = set()   # 同父块的兄弟子块只保留一条，防上下文重复

    for i, h in enumerate(hits):
        parent_key = h.parent_id or h.chunk_id
        if parent_key in seen_parents:
            continue
        seen_parents.add(parent_key)

        content = h.parent_content          # 优先用冗余的 parent_content，省一次 DB 往返
        if content is None and parent_lookup is not None and h.parent_id:
            content = await parent_lookup(h.parent_id)
        blocks.append(EvidenceBlock(..., content=content or h.content, label=f"S{i + 1}"))

    ordered = u_shape_order(blocks, budget_tokens)
    for i, b in enumerate(ordered):        # 重新打 label：U 型排序后顺序变了，label 必须跟最终顺序一致
        b.label = f"S{i + 1}"
    return ordered
```

四个决策：

- **父块优先**：`chunks.parent_content` 是 R2 写入的冗余列——top5 子块直接带父块内容，一次 DB 往返都省掉。只有 Hit 没带父块内容且调用方给了 `parent_lookup` 时才回查。**判定需要完整章节上下文**（R2 的"达梦/金仓"例子），子块单独喂给 LLM 一定会漏判 PARTIAL。
- **兄弟子块去重**：同一小节的多个子块都命中时，父块内容一样，只保留一条。不去重的话 6000 token 预算被同一节内容占三份。
- **U 型排序**：`lost-in-the-middle` 的对策——模型注意力偏爱开头和结尾。第 1 名放头、第 2 名放尾、第 3 名放头……**排序发生在预算裁剪之前还是之后，直接决定谁被裁**：`u_shape_order` 从头累加预算，超预算的 `continue`（不 break——后面可能有更短且重要的片段）。
- **label 重打**：U 型排序后顺序变了，`[S1][S2]` 必须跟最终顺序一致。A6 的证据回查按 label 反查原文——label 和内容错位，回查全乱。

## 本阶段术语

> 【白话】**RRF（倒数排名融合）**：把两路检索结果都换成"第几名"，按 1/(60+名次) 计分合并。两路都命中的段落天然分高。
> 【白话】**logprobs**：模型输出每个 token 的对数概率。重排器用 yes/no 的 logprob 还原 0-1 连续分数——拒答阈值靠它成立。
> 【白话】**降级链**：主方案挂了按优先级切备选，且切走时打标记。静默降级是质量滑坡的开始。
> 【白话】**U 型排序**：最重要的证据放头尾，次要的放中间。模型对中间内容的注意力天生弱。
> 【白话】**lost-in-the-middle**：长上下文里，模型对中间段落的内容利用率明显低于头尾。长证据链必须重排，不能按相关度顺序平铺。

## 完成标准

- RRF 单测：双命中 chunk 分数严格大于任一单命中；量纲无关性（给两路注入不同量纲分数，融合结果只取决于名次）
- `yes_no_probability` 单测：top_logprobs 缺 yes/no → 抛错（不返回猜测值）
- 降级演练：mock 重排超时 → `degraded='no_rerank'` 且 trace 有标记、结果按 RRF 序输出
- 组装单测：①同父块兄弟子块去重 ②超预算时"更短的后续片段"仍有机会入选（continue 语义）③label 与最终顺序一致
- 端到端：真实评分项走完 R4→R5，人工检查 top5 证据块的"父块完整性"——判定需要的上下文（正文+附件清单+计划）在不在
- 拒答路径可演示：构造一个方案里没写的评分项，重排 top1 < 0.15，输出 NOT_FOUND（这是**合法结论不是故障**）
