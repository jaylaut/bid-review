## 这个阶段只干一件事

把 markdown 切成"检索用得起、判定用得上"的块。

这是本项目 RAG 的成败关键，值得把道理讲透：评分项"支持国产数据库适配"，应答往往**分散在三个地方**——

```
3.2.4 正文：   "平台已完成达梦 DM8 的适配测试"（一句承诺）
附件清单：      "附件 12：国产数据库适配验证报告 V2.1"（证明材料编号）
实施计划：      "第 3 阶段完成金仓兼容性验证"（时间表）
```

**只给子块会漏判"部分响应"**：向量命中的是 3.2.4 那句承诺，模型看到"已完成适配"，判 PASS——漏掉了"提了达梦没提金仓"。给整节才能看出缺口。父子块设计就是为这个场景生的。

## 第一层：按标题层级切节

```python
HEAD_RE = re.compile(r"^(#{1,6})\s+(.*)$")

def markdown_to_sections(md: str, ...) -> list[Section]:
    for block in re.split(r"\n(?=#)", md):
        m = HEAD_RE.match(lines[0])
        if m:
            level = len(m.group(1))
            counter[level] = counter.get(level, 0) + 1
            for lvl in list(counter):        # 更深层级计数重置
                if lvl > level:
                    del counter[lvl]
            num = ".".join(str(counter[lvl]) for lvl in sorted(counter) if lvl <= level)
            sec = Section(title=..., level=level, path=f"{path_prefix}{num}", ...)
```

产出 `Section` 树（扁平列表带 path）：`"3>3.2>3.2.4"`。

**`section_path` 是分块的核心字段**，它同时是两样东西的统一坐标：

1. **引用定位**："依据：投标文件 技术部分 3.2.4，P87"——人工抽查、前端高亮、A6 证据校验都靠它；
2. **父块回溯**：检索命中子块 → 按 `parent_id` 找回父块。

path 断了（编号跳级、幽灵层级），引用和回溯一起瘸。R1 的 `normalize_markdown` 跳级纠正确保了层级连续——这就是两个阶段之间的隐藏依赖。

参数（`config/rag.yaml`，R0 已落）：

| 参数 | 值 | 为什么 |
| --- | --- | --- |
| `max_tokens` | 512 | 子块入向量库被检索。512 是"一个语义完整单元"的经验值，再大向量被多主题稀释 |
| `overlap_tokens` | 64 | 关键句恰好跨切点时，两块各有一份，检索至少命中一次 |
| `parent_max_tokens` | 2000 | 父块喂 LLM 判定。2000 token 是"完整但不爆上下文"的平衡 |

> 【why】按句子边界切而不是定长硬切：定长切会把"支持达梦 DM8"从"适配测试"中间劈开，两边都不是完整语义，向量表示双双劣化。句子边界 + 64 重叠是低成本高保真的组合。

## 父子块：本项目用法的具体形态

```python
for sec in sections:
    # 父块内容：整节。超长截断——判定时给 LLM 的上下文要完整但有限
    parent_content = content
    if approx_tokens(parent_content) > parent_max_tokens:
        parent_content = parent_content[: parent_max_tokens * 2]
        truncated = True

    parent_id = next_id()

    # 表格整块（markdown |---| 格式），绝不切开
    if content.startswith("|") and "\n|" in content:
        out.append(Chunk(parent_id, ..., kind="table", ...))
        continue

    pieces = _split_long_text(content, max_tokens, overlap_tokens)
    for piece in pieces:
        out.append(Chunk(next_id(), ..., kind="text", ...))

    # caption 单独成块（图注），不参与正文切分
    for m in re.finditer(r"^(图\s*\d+[：:].+)$", content, flags=re.MULTILINE):
        out.append(Chunk(next_id(), ..., kind="caption", ...))
```

三条特殊规则，每条都对应一类真实标书内容：

- **表格整块不切**（`chunk_kind='table'`）：评分办法、参数表切开后，表头和单元格分家，检索回来一堆没头没脑的数字。表格单独成块，且 R4 的稀疏路能整表匹配。
- **caption 单独成块**（`chunk_kind='caption'`）：图注（"图 12：系统部署架构"）往往是图和正文之间的桥梁。它**不参与正文检索**——R4 的 `SQL_DENSE` 里 `chunk_kind <> 'caption'` 就是为这个：图注太短，向量表示没信息量，混进结果池只会稀释 top5。
- **短节 = 单片段**：子块即节本身，不强行凑父子结构。

## uuid5 确定性 ID：幂等的前提

```python
def next_id() -> str:
    # 【why】uuid5 确定性 ID：同文档重入库时同一 chunk 得到同一 ID，
    # 配合 ON CONFLICT 幂等覆盖；uuid4 会让每次入库都产生新行
    nonlocal counter
    counter += 1
    return str(uuid.uuid5(uuid.NAMESPACE_URL, f"{doc_ref}:{counter}"))
```

这行是 R3 幂等入库的前提：**chunk_id 由 (doc_ref, 序号) 确定性派生**，同一文档第二次入库，第 37 号块还是第 37 号块的 ID，`ON CONFLICT (chunk_id) DO UPDATE` 直接覆盖。用 uuid4 的话每次入库都是全新 UUID，旧块只能软删、新块只能插入，表无限膨胀，对账永远对不上。

注意一个隐含前提：`doc_ref` 必须稳定（R3 用 `documents.doc_id`，由 `(project_id, file_sha256)` 幂等产生）——**上游不稳，下游的确定性全是假的**。

## 本阶段术语

> 【白话】**父子块**：小块（512 token）负责被检索到，大块（整节 ≤2000 token）负责给 LLM 看全貌。检索要准，判定要全，一对矛盾用两级结构同时满足。
> 【白话】**section_path**：块的章节坐标（"3>3.2>3.2.4"）。引用定位和父块回溯共用它，是整条证据链的锚。
> 【白话】**递归切分**：超长内容按句子边界一段段切，每段仍不超限就继续。不是定长硬斩。
> 【白话】**重叠（overlap）**：相邻两块共享 64 token 的尾巴。关键句跨切点时，至少有一块完整拥有它。
> 【白话】**确定性 ID**：同样输入永远算出同样 ID（uuid5）。它是幂等覆盖的前提；uuid4 的随机 ID 会让"重新入库"变成"重复入库"。
