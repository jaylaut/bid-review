## 这个阶段只干一件事

把块变成"可检索的资产"，且**任何一步失败都能重跑，重跑不产生副作用**。

离线管道是重 IO + 慢计算（嵌入 30–90s/文档），中途失败是常态不是异常。设计目标只有一个：**崩在哪一步，就从哪步接着跑，已完成的块不重做、不重复**。

## 嵌入 Provider：四条铁律

`models/embedding.py` 的模块 docstring 就是铁律清单，每条背后都是一个静默失败：

```python
# 1. 查询侧必须带指令，文档侧不带——Qwen3 指令感知，两侧不对称是模型设计如此
QUERY_INSTRUCTION = "Instruct: 检索投标技术方案中响应以下技术要求的段落\nQuery: {评分项文本}"

# 2. num_ctx 必须显式传，否则长文本静默截断
options = {"num_ctx": 1024}

# 3. 返回向量必须已归一化（L2≈1），配合内积索引
if abs(norm - 1.0) > 1e-2:
    raise ContractViolation(f"嵌入向量未归一化（L2={norm:.4f}），内积索引会算错相似度")

# 4. 维度必须 == EMBEDDING_DIM，不一致在第一次调用就炸
if len(vec) != dim:
    raise ContractViolation(f"嵌入维度 {len(vec)} != 配置 {dim}（检查 EMBEDDING_MODEL 是否被换过）")
```

【why】第 3、4 条为什么要"当场炸"而不是记警告：维度不匹配如果 DDL 恰好兼容（比如 768 维数据进 1024 维列被 PG 拒绝还算幸运），真正的灾难是**语义错位但不报错**——向量能存、能查、有结果，只是全错。这类 bug 能藏三个月。宁可按停管道，不要带着暗病跑。

**指令不对称的后果**：查询带 `Instruct:`、文档不带，两侧向量才落在同一语义空间。两侧都带或都不带，Hit@5 会凭空掉 10 个点以上，且你从日志里看不出任何异常。指令文本变更 = 新 `embedding_ver` = 全量重嵌入（R0 已讲，这里是执行点）。

## index_document：一条文档的完整管道

```python
async def index_document(md_text, *, project_id, doc_type, title, file_hash, acl,
                         embedding_ver, chunking_ver, ...) -> IndexResult:
    """markdown → 分块 → 嵌入 → 幂等入库。"""
```

### 幂等第一级：文档级，且必须看 status

```python
# 【坑·真库验证发现】只看"记录存在"会漏掉写入中途失败的文档：
# 上次跑崩在嵌入/写块阶段时 documents 已有记录但 chunks 为空，
# 重跑直接 skip = 数据永久缺失。必须 status='indexed' 才算真完成。
existing = await fetch(
    "SELECT doc_id FROM documents WHERE project_id=$1 AND file_sha256=$2 "
    "AND status='indexed'",
    (project_id, file_hash))
if existing:
    return IndexResult(doc_id=existing[0]["doc_id"], chunks_written=0, skipped=True, ...)
```

这个坑值得单独说：管道崩在"文档记录已建、块没写完"的中间态时，**朴素的幂等判断（记录存在 → skip）会把失败永久化**。重跑十次跳过十次，数据缺口到对账那天才发现。幂等的判据不是"留过痕"，是"做完了"。

### 幂等第二级：事务内软删 + 写新块

```python
async def _write(conn) -> None:
    await conn.execute("UPDATE chunks SET status='deleted' WHERE doc_id=$1", doc_id)
    for i, c in enumerate(chunks):
        await conn.execute("""
            INSERT INTO chunks (...) VALUES (...)
            ON CONFLICT (chunk_id) DO UPDATE SET ... status='active', ...
        """, ...)
async with transaction() as conn:
    await _write(conn)
```

**不先删后写**：先 DELETE 再 INSERT，中途失败就是"旧的没了新的也没写"，两边都没有。软删 + 事务保证要么旧块还在（失败），要么新块全就位（成功）。

配套 R2 的 uuid5 确定性 ID：同文档重入库 → 同 chunk_id → `ON CONFLICT DO UPDATE` 覆盖。软删的旧块由后续物理清理任务回收。

### 一个待修的不一致：向量存储格式

```python
# indexer 当前写法：
json.dumps(vec)   # jsonb 暂存向量；pgvector codec 注册后改原生

# 但 common/db.py 已经做了：
from pgvector.asyncpg import register_vector
await register_vector(conn)   # 每个池连接建立时注册
```

`common/db.py` 已给每个连接注册 pgvector codec（`vector` 列直接收 `list[float]`），indexer 却还在 `json.dumps(vec)` 传字符串——**两条路只对齐一条**。落地 R3 时把 `json.dumps(vec)` 改回传 `vec` 原生 list，否则要么存储格式错、要么 codec 报 DataError。注释里"注册后改原生"的 TODO 就是留给这一步的。

## 换模型 / 换分块：蓝绿切换

```
新 embedding_ver / chunking_ver → 新版本数据并行入库 → 评测对比 → 旧版下线
```

**不要原地覆盖**。原地重切的三个问题：①嵌入到一半中断，新旧向量混在一张表，检索结果时好时坏；②回滚没有旧数据可回；③没法对比"新旧哪个好"——评测对比要求两个版本同时可查。蓝绿是离线数据管线的标准做法，成本只是双倍存储。

## 每日对账

```sql
-- count(documents.status='indexed') == count(distinct chunks.doc_id)
-- 不一致率 >0.1% 告警
```

对账抓三类问题：①管道中途失败留下的 `indexing` 僵尸文档；②软删未物理清理导致的计数虚高；③R1 命名覆盖导致的"解析了但没入库"。**每日定时跑，告警进消息群**——数据管道的信任是攒出来的，也是这么守住的。

## MQ 编排：ingest worker

```
消费消息 {doc_id} → 状态机: parsing → cleaning → chunking → embedding → indexing → indexed
每步落 DB 进度 + 发 progress 事件（Java SSE 转推前端）
失败：重试 3 次（指数退避）→ 死信队列 → 人工介入
prefetch=2：解析是重 IO，防止 worker 内存被打爆（背压）
```

四个要点：

- **状态机落 DB 不落内存**：worker 崩了重启，新 worker 读 `documents.status` 就知道每个文档干到哪了——和 A4 的 checkpointer 同一个思想，离线版。
- **重试 3 次 + DLQ**：标书解析失败很常见（加密 PDF、损坏文件），但重试救不了"文件本身坏了"——3 次进死信，人工介入，不无限重试烧钱。
- **prefetch=2 背压**：一次预取 2 条，处理完再取。解析一份标书吃几百 MB 内存，prefetch 开大 = worker 排队 OOM。
- **progress 事件**：每步发一次，Java 侧 SSE 转推前端。用户看到"正在嵌入（45/900）"和看到转圈十分钟，是两回事。

> RocketMQ 真连未验证（11 §P1.2/1.4），ingest worker 的 MQ 部分等真连后再落地；在那之前，`index_document` 可以脚本直调跑通管道——**先证明管道对，再接消息**。

## 本阶段术语

> 【白话】**幂等**：同一操作执行多次，结果和执行一次相同。重跑不重复、不覆盖出错的数据。
> 【白话】**软删**：不物理删除，把 status 标成 deleted。事务保安全，物理清理事后做。
> 【白话】**蓝绿切换**：新版本数据并行建好，评测对比后再切流量，旧版留作回滚。数据管道不许原地覆盖。
> 【白话】**背压（prefetch）**：消费者处理不过来时限制预取数量，防止内存被打爆。重 IO 管道的保命阀。
> 【白话】**死信队列（DLQ）**：重试多次还失败的消息进这里，人工处理。给救不了的失败一个体面的归宿。

## 完成标准

- 同一文档连续 `index_document` 两次：第二次 `skipped=True`，chunks 行数不变（`SELECT count(*)` 前后一致）
- 人为在嵌入阶段抛异常中断第一次入库，重跑：最终 chunks 数量正确，无僵尸 `indexing` 文档
- 换 `embedding_ver` 重跑同一文档：新旧版本数据并存（蓝绿），检索时可指定版本
- 每日对账脚本跑出 0 不一致；人为删一个 chunk 制造 0.5% 不一致，确认告警触发
- `grep -n "json.dumps(vec)" src/rag/offline/indexer/__init__.py` 无结果（向量改原生 list 传递）
- ingest worker 脚本直调模式跑通 3 份文档全管道；MQ 模式等 RocketMQ 真连后补验
