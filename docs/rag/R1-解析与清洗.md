## 这个阶段只干一件事

把"原件 → 干净的 markdown"做对，且每一步可单测、可重跑、可对账。

管道设计原则：**离线阶段的所有错误都要在离线暴露**。解析漏一段、清洗删一行正文，在线检索阶段只会表现为"某条评分项老是找不到依据"——那时候你没有任何线索指回解析器。

## 解析路由：先探针，再决定用什么解析器

```
输入文件 → 快速探针（抽前 10 页）:
  文本密度 < 0.05           → MinerU-VLM 通道（扫描件/图片型，PaddleOCR 兜底）
  其余（原生 docx/pdf/doc） → MinerU pipeline 通道
```

```python
def detect_route(sample_pages: list[str]) -> ParseRoute:
    if not sample_pages:
        return ParseRoute("mineru", "空文档按默认通道（MinerU pipeline）")
    total_chars = sum(len(re.sub(r"\s", "", p)) for p in sample_pages)
    total_area = sum(max(len(p), 1) for p in sample_pages)
    density = total_chars / total_area
    if density < 0.05:
        return ParseRoute("mineru-vlm", f"文本密度 {density:.3f} < 0.05（扫描件）")
    return ParseRoute("mineru", f"文本密度 {density:.3f}（文本型，MinerU pipeline）")
```

三个设计决定，都不是随手选的：

- **0.05 是扫描件分界线**：扫描件每页 OCR 出来的是零散字符块，文本密度天然低一个量级；原生 PDF/docx 一页轻松上千字符。0.05 落在两者之间的空档里。
- **统一 MinerU，不上多解析器**：既定方案（06/03 均已同步）。解析器越多，产物格式越分裂，R2 分块要兼容的 markdown 方言就越多。**一个解析器 + 两种模式**是收敛成本的最优解。
- **探针只抽前 10 页**：整本跑一遍探针比解析本身还慢。前 10 页足够判断"这本是不是扫描的"——没有哪本标书前 10 页是正文、后面突然全是图片。

### 重依赖惰性接入

MinerU（magic-pdf）是重依赖，未安装时给**可落地的报错**而不是裸 `ImportError`：

```python
def parse_with_mineru(path: str) -> str:
    try:
        from magic_pdf.data.data_reader_writer import FileBasedDataReader
    except ImportError as e:
        raise ConfigError(
            "MinerU（magic-pdf）未安装。安装：uv add magic-pdf。\n"
            "纯调试下游（分块/嵌入/检索）可先用 parse_plain_text 通道跑通全链路。"
        ) from e
```

`parse_plain_text` 是纯文本兜底通道（.txt/.md 直读）：**调试下游时不必先啃解析器**，用 txt 走通 R2–R5 全链路，解析器最后接上。这是"管道可分段验证"的关键一招。

### normalize_markdown：跳级纠正

```python
# 真实标书的 markdown（MinerU 导出）常出现 # 直接跳 ###，
# 分块的层级计数会乱。规整后 markdown_to_sections 的编号才连续。
if prev_level and level > prev_level + 1:
    level = prev_level + 1       # 跳级压回
```

> 【坑】不纠正跳级的后果在 R2 才爆炸：`markdown_to_sections` 按标题级别累加编号（3 → 3.2 → 3.2.4），遇到 `#` 直接跳 `###` 会切出幽灵层级，`section_path` 出现 "3>1" 这种断档——引用定位（"依据：3.2.4 节 P87"）全错，而且不报错。

## 清洗：规则清单（标书特化）

```
页眉页脚（跨页重复行检测，阈值 0.8）→ 水印文字 → 零宽字符 → 目录/封面剔除
→ 精确去重（content hash）→ 近重复（Jaccard 0.85）
```

```python
def clean_document(pages: list[str]) -> list[str]:
    pages = [strip_zero_width(p) for p in pages]
    pages = [strip_watermark(p) for p in pages]
    pages = remove_headers_footers(pages)
    return [re.sub(r"\n{3,}", "\n\n", p).strip() for p in pages]
```

三条规则背后的道理，比规则本身重要：

- **页眉页脚用"比例"而不是"固定次数"**：3 页文档出现 3 次是页眉，300 页文档出现 3 次不是。
- **少于 3 页不做页眉检测**：单页文档任何行都是 100% 重复，正文会被整体误删——样本不足以区分"页眉"和"唯一一行正文"。这是会静默毁掉整份文档的坑。
- **零宽字符是清洗 + 防注入双用途**：`"忽"+U+200B+"略"` 这类拼接可以绕过关键词检测（电子书 25.3），入索引前废掉，检索侧和注入防御同时受益。

**不做 PII 脱敏**——这是与通用知识库的又一个差异。标书本身就是给评审看的，公司名、人名、电话正是证据链的一部分，脱敏反而毁掉"依据：xxx 公司 P87"的举证能力。

### 近重复：Jaccard 逐对比对，不上完整 MinHash

```python
def near_duplicate_hash(text: str, shingle: int = 5) -> set[str]:
    """字符 shingle 集合（MinHash 的极简替身）。"""
    t = normalize_ws(text)
    if len(t) < shingle:
        return {t}
    return {t[i : i + shingle] for i in range(len(t) - shingle + 1)}
```

【why】文档级清洗阶段用 Jaccard 逐对比对，量级（百页级）完全够；**万级 chunk 再考虑 LSH**（R2 的 `dedupe_chunks` 用的是同一套函数，chunk 量级先用 Jaccard，真慢了再升 LSH——顺序别反，先上 LSH 是给百页文档造航天飞机）。

## 质量门：解析产物不是全都可信

```
解析结果按 0-8 打分（电子书 4.6）：
  <6 → 进人工复核队列（抽检 5%）
```

标书解析失败很常见：加密 PDF、损坏文件、扫描件模糊到 OCR 出来全是乱码。**质量门的价值是把"静默的坏数据"变成"显式的队列"**——没有它，乱码 chunk 会安静地进库，然后在某个评分项上表现为"检索不到"，你查一个星期都查不到解析器头上。

## 命名坑：解析产物会互相覆盖

这是 [11 §P0 坑预警](../11-总体开发路线（RAG+Agent+Java）.md) 记录的真实风险：

> 解析产物现按 `tender_{日期}.md` 命名，10 月多个日期有 2–15 个同日期项目，**命名键会互相覆盖**。

```text
tender_2026-10-12.md   ← 10-12 有 3 个项目，跑一个覆盖一个
```

落地时必须二选一：

1. 改用**完整项目编号**命名（推荐，编号天然唯一且可追溯）；或
2. 维护 `data/parsed/manifest.json`：`{项目编号: {raw_sha256, parsed_path, parse_backend, quality_score, ts}}`。

`scripts/check_parse_sync.py` 已提供 raw ↔ parsed 对账能力——**每天跑一次**，`raw 里有、parsed 里没有` 和 `命名键冲突` 都会现形。覆盖类 bug 的可怕之处在于它不报错，只是安静地少数据。

## 本阶段术语

> 【白话】**文本密度**：一页里非空白字符占总字符的比例。扫描件密度低一个量级，用它做路由探针。
> 【白话】**页眉页脚检测**：跨页重复出现的短行（≥80% 页面都有）判为页眉页脚删掉。少于 3 页不判——样本不够。
> 【白话】**Jaccard 相似度**：两个集合的交集 / 并集。用来判断两段文字是不是"差不多的重复"。
> 【白话】**质量门**：解析产物先打分，低分进人工队列。把静默的坏数据变成显式的待办。
> 【白话】**manifest**：产物登记表。数据管道的"账本"，没有它就不知道谁覆盖了谁。
