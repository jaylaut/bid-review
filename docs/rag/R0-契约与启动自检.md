## 三张表：一表一职责

```sql
-- documents：权威元数据。电子书 3.1 的教训——元数据不只放向量库
CREATE TABLE documents (
    doc_id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id      VARCHAR(64)  NOT NULL,          -- 项目隔离的第一道闸
    doc_type        VARCHAR(32)  NOT NULL,          -- bid_doc | bid_response | reference
    title           TEXT,
    file_sha256     CHAR(64)     NOT NULL,          -- 幂等键
    file_uri        TEXT         NOT NULL,          -- MinIO 路径
    parse_backend   VARCHAR(32),                    -- mineru | mineru-vlm
    parse_quality   SMALLINT,                       -- 0-8 质量分（R1 质量门）
    acl             JSONB        NOT NULL,          -- ["proj:xxx","sec:标段1","lvl:公开"]
    status          VARCHAR(24)  NOT NULL,          -- uploaded|parsing|indexed|failed|deleted
    embedding_ver   VARCHAR(64)  NOT NULL,          -- 换嵌入模型/指令 = 新版本 = 重嵌入
    chunking_ver    VARCHAR(32)  NOT NULL,          -- 换分块策略 = 新版本
    created_by      VARCHAR(64),
    created_at      TIMESTAMPTZ  DEFAULT now(),
    UNIQUE (project_id, file_sha256)
);
```

`status` 是 R3 幂等的生死字段：**只有 `status='indexed'` 才算真完成**。只看"记录存在"会漏掉写入中途失败的文档——上次跑崩在嵌入/写块阶段时 `documents` 已有记录但 `chunks` 为空，重跑直接 skip = 数据永久缺失。这个坑是真库验证踩出来的，见 R3。

```sql
-- chunks：chunk + 向量 + 全文，一表三列（03 §3.2）
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS zhparser;

CREATE TABLE chunks (
    chunk_id        UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    doc_id          UUID NOT NULL REFERENCES documents(doc_id) ON DELETE CASCADE,
    project_id      VARCHAR(64) NOT NULL,           -- 冗余存储：过滤时免 join
    parent_id       UUID,                            -- 父块回溯（R2 父子块设计）
    section_path    TEXT,                            -- "3>3.2>3.2.4 数据库兼容性"
    section_title   TEXT,
    page_start      SMALLINT, page_end SMALLINT,    -- 引用定位：页
    bbox            JSONB,                           -- 引用定位：坐标（可点击高亮）
    content         TEXT NOT NULL,                   -- 子块正文（≤512 token）
    parent_content  TEXT,                            -- 父块正文（≤2000 token，判定用）
    token_count     SMALLINT,
    chunk_kind      VARCHAR(16) DEFAULT 'text',      -- text|table|list|caption
    acl             JSONB NOT NULL,
    embedding       vector(1024) NOT NULL,           -- 归一化后用内积
    status          VARCHAR(16) DEFAULT 'active',    -- active|deleted（R3 软删）
    tsv             tsvector GENERATED ALWAYS AS
                    to_tsvector('zh', content) STORED,  -- zhparser 中文全文
    created_at      TIMESTAMPTZ DEFAULT now()
);
```

> 【DDL 差异】03 §3.2 原始 DDL 没有 `status` 列，§4.5 的软删策略需要它——建表时补一列 `status VARCHAR(16) DEFAULT 'active'`。**设计文档与实现的差异要记录在代码注释里**（`rag/offline/indexer/__init__.py` 已注明），否则下次对文档的人会以为漏建了列。

三路索引，一个都不能少：

```sql
CREATE INDEX idx_chunks_vec ON chunks
    USING hnsw (embedding vector_ip_ops)            -- m=16, ef_construction=200
    WITH (m = 16, ef_construction = 200);
CREATE INDEX idx_chunks_tsv ON chunks USING gin (tsv);
CREATE INDEX idx_chunks_filter ON chunks (project_id, doc_id, chunk_kind);
CREATE INDEX idx_chunks_acl ON chunks USING gin (acl);
```

**pgvector 四个静默失败的防御**（电子书 8.6）：①必须显式建 HNSW 索引（否则全表扫，无任何警告）②1024 维已控制成本 ③距离函数统一内积（向量已归一化）④高并发加 PgBouncer。四项由 R0 的启动自检验证，任何一项不满足直接 fail-fast。

```sql
-- scoring_items：链路 A 的产物，链路 B（RAG）的查询来源
CREATE TABLE scoring_items (
    item_id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id      VARCHAR(64) NOT NULL,
    item_code       VARCHAR(32),                    -- "S3.2.4"
    category        VARCHAR(64),                    -- 技术参数|实施能力|资质|服务
    item_text       TEXT NOT NULL,                  -- "支持国产数据库（达梦、人大金仓）适配"
    weight          NUMERIC(5,2),                   -- 分值
    requirement     JSONB,                          -- {must:[...], evidence_required:[...]}
    source_ref      JSONB                           -- 招标文件中的位置 {page, section_path}
);
```

`requirement.must` 是把评分项拆成**可验证的原子要求**——它是 R4 查询构造的关键词来源，也是 Agent 判定 `missing_aspects` 的依据。填表时图省事留空，后面检索和判定一起瘸。

## 两个版本号：embedding_ver 与 chunking_ver

这是全项目最容易被忽视、事后最贵的两个字段：

```
embedding_ver = "qwen3-emb-0.6b@1024@v1@ip@<instr_hash>"
                模型        维度  版本 距离  查询指令哈希
chunking_ver  = "structural_recursive@v1"
```

- **查询侧指令变更 = 新 embedding_ver = 全量重嵌入**。Qwen3 是指令感知模型，`Instruct:` 那段文本改了，查询向量语义就变了，旧向量的相似度全部失真——且不报错。所以指令文本的 sha256 必须哈希进版本号，启动时校验。
- **分块策略变更 = 新 chunking_ver = 重新入库**。512 改 400、重叠 64 改 128，产出的块和旧块混在一张表里，检索结果时好时坏，查都没法查。
- 两者共同构成 R3 蓝绿切换和 R7 评测对比的坐标：**每个结论都必须能回答"当时用的哪个版本"**（A0 的 EngineMeta 同理）。

## 七项 fail-fast 启动自检

`scripts/check_env.py` 已落地。逻辑：**启动时把环境问题一次性全部暴露，而不是等第一次查询时静默出错**。

| # | 检查项 | 失败含义 |
| --- | --- | --- |
| 1 | PG 连接 | 后面全部免谈 |
| 2 | pgvector 扩展 | 无向量列 |
| 3 | zhparser 扩展 + `zh` 配置 | 稀疏路直接死（官方 pgvector 镜像不含 zhparser，须用 `deploy/postgres` 自建镜像） |
| 4 | chunks 表 HNSW 索引存在 | 没建索引 = 全表扫，且**无任何警告** |
| 5 | DDL 向量维度 == EMBEDDING_DIM | DDL 恰好兼容但语义错位，检索结果全错还不报错 |
| 6 | Ollama 嵌入：num_ctx ≥ 1024 且返回维度/归一化正确 | 长 chunk 静默截断；未归一化则内积算错相似度 |
| 7 | Ollama 重排 logprobs 探针 | 拿不到 logprobs → 无法还原 0-1 连续分数 → R5 的拒答阈值 0.15 失效 |

> 【why】fail-fast 而不是 lazy check：标书检索的失败模式大多是**静默的**——维度不匹配可能不报错、没建索引只是慢 100 倍、logprobs 缺失只是让阈值永远不触发。这些问题在"第一次真实查询"时暴露，就是线上事故；在启动时暴露，就是一行日志。

## config/rag.yaml：配置驱动

对齐 03 §八。**阈值全部进配置，不散落在代码里**——R7 的阈值标定要改的就是这个文件，硬编码在代码里的话每次标定都是一次发版。

```yaml
rag:
  offline:
    parsing:
      router: {scanned_threshold: 0.05}        # R1 探针阈值
      backends: {default: mineru, scanned: mineru-vlm}
      quality_gate: {min_score: 6, sample_rate: 0.05}
    cleaning:
      dedupe: {exact: true, near: {method: minhash, threshold: 0.85}}
    chunking:
      strategy: structural_recursive            # R2
      max_tokens: 512
      overlap_tokens: 64
      parent_max_tokens: 2000
      special: {table: whole, caption: standalone}
    embedding:
      provider: ollama                          # 换 = 重嵌入（见 embedding_ver）
      model: qwen3-embedding:0.6b
      dim: 1024
      distance: ip                              # Ollama 返回已归一化 → 内积
      query_instruction: "Instruct: 检索投标技术方案中响应以下技术要求的段落\nQuery: "
      serving: {endpoint: "http://localhost:11434", batch_size: 32, num_ctx: 1024}
    indexing:
      hnsw: {m: 16, ef_construction: 200, ef_search: 128}
      reconcile: {cron: "0 3 * * *", alert_threshold: 0.001}
  online:
    retrieve:
      dense_k: 60
      sparse_k: 60
      fuse: {method: rrf, k: 60, pool: 100}
      sparse_weight: 1.0                        # 型号类漏检时升 1.2（R7 单变量实验）
    rerank:
      provider: ollama-qwen3
      model: dengcao/Qwen3-Reranker-0.6B:Q8_0
      candidates: 20
      top_n: 5
      refusal_threshold: 0.15                   # R7 标定，不是拍的
      fallback: cloud_then_rrf
    assemble:
      context_budget_tokens: 6000
      order: u_shape
    cache:
      l1_ttl: 24h
      l2_ttl: 168h
      l3_enabled: true
```

## 在线链路契约：RetrieveQuery 与 Candidate

```python
class RetrieveQuery(BaseModel):
    """检索入参。构造是确定性模板（agent/query.py，见 R4），零 token 成本。"""
    item_id: str
    query_text: str                     # 评分项原文 + must 要点拼接
    keywords: list[str] = []            # 喂稀疏路：型号/标准号/名词短语
    embedding: list[float] = []         # 调用方先算好（含查询侧指令）
    project_id: str                     # 权限过滤第一闸
    acl: list[str] = []
    top_k: int = 5

class Candidate(Hit):
    """召回候选：Hit + 双路各自的名次（RRF 融合要用）。"""
    dense_rank: int | None = None       # 向量路名次（1-based），未命中 None
    sparse_rank: int | None = None      # 全文路名次
    rerank_score: float | None = None   # 重排后分数（可能被降级标记污染，看 degraded）
```

两条契约纪律：

1. **`embedding` 由调用方算好再传进来**，`retrieve()` 不自己调嵌入——R6 的 L1 缓存要复用同一个向量，检索函数内部算的话缓存无处安放。
2. **`Candidate` 必须带两路各自的名次**。RRF 只信名次不信分数（两路量纲不同，见 R5），名次丢了融合就没法做。

## 本阶段术语

> 【白话】**fail-fast**：启动时把问题全查一遍，有一个不满足就当场退出。宁可起不来，也不要带着暗病跑。
> 【白话】**embedding_ver**：嵌入方案的版本号。模型、维度、距离算子、查询指令，任何一个变了都是新版本——旧向量不重嵌就会静默失真。
> 【白话】**HNSW**：向量的近邻索引。不建它，每条查询都全表扫描——慢，而且不报错。
> 【白话】**内积（ip）**：已归一化向量用内积等于余弦相似度。距离算子和索引必须配套，混用即静默错误。
> 【白话】**tsvector / zhparser**：PG 的中文全文检索。中文没有空格分词，必须靠 zhparser 的 `zh` 配置，官方镜像默认不带。
