## 这个阶段只干一件事

让"重复的检索"不重复花钱，且**缓存失效永远偏安全**。

缓存在 RAG 里首先是**正确性问题，其次才是性能问题**——键设计错一次的后果不是慢，是**拿旧内容判新方案**。

## 键设计：三个字段一个不能少

```python
def sha256_key(*parts: Any) -> str:
    """多部分键：任意对象 → json(有序) → sha256。"""
    raw = json.dumps(list(parts), ensure_ascii=False, sort_keys=True, default=str)
    return hashlib.sha256(raw.encode()).hexdigest()
```

| 层 | 键 | 值 | 命中场景 |
| --- | --- | --- | --- |
| L1 嵌入缓存 | `sha256(query_text)` | 查询向量 | 同评分项重试/版本比对 |
| L2 检索缓存 | `sha256(item_id + doc_version + params_hash)` | 候选+重排结果 | 方案微改后重评：未变章节全命中 |
| L3 判定缓存 | `sha256(item_id + doc_version + prompt_version)` | 完整 Verdict | **同一方案二次评审 token 成本≈0** |

三个键里的隐藏字段，全是正确性防线：

- **L2 必须含 `doc_version`**：投标方改了方案（哪怕改一页），旧缓存不失效 = **拿旧内容判新方案**。评标场景这是事故级错误。
- **L3 必须含 `prompt_version`**：否则提示词优化永远"看不见效果"——缓存里躺着旧 prompt 的结论，你改了 prompt 重跑，出来的还是老结论，调优全部失效。
- **`sha256_key` 统一构造**：散落各处的 f-string 拼接会出现分隔符歧义（`"a|bc"` vs `"ab|c"` 撞同一个键）——哈希前用 `json.dumps(sort_keys=True)` 规范化，从机制上杜绝。

## 缓存故障：绝不拖垮主链路

```python
async def get(self, level: str, key: str) -> Any | None:
    try:
        ...
    except Exception:
        return None      # 【why】缓存故障绝不拖垮主链路：读失败当 miss

async def put(self, level: str, key: str, value: Any, ttl: int) -> None:
    try:
        ...
    except Exception as e:
        logging.getLogger(__name__).debug("cache put failed: %s", e)   # 写失败静默但留痕
```

两条纪律：

- **读失败当 miss，写失败静默**：缓存是优化不是依赖。Redis 挂了，检索链路照常跑（只是慢）；绝不能因为缓存层故障让整个评审失败。
- **写失败留 debug 日志**：静默但不无声。命中率莫名其妙下降时，这条日志是唯一线索。

## 延迟预算：两段分开看

```
检索段（不含重排）：查询嵌入 100–300ms ‖ 双路召回 60ms → RRF 5ms → 组装 10ms → 合计 < 400ms
重排段：            Ollama Qwen3-Reranker CPU 约 0.5–1.5s/对 × 20 候选 = 10–30s/评分项
```

**瓶颈在重排，不在检索**。所以优化方向是先动重排：

- 检索段已经够快（实测 0–15ms），优化它没有意义；
- 重排段是数量级瓶颈，三个解法按优先级：①80 项并发摊薄（A7 调度器，信号量 8）②候选降 12（单变量实验验证损失，03 §5.4 开关）③重排走云 API 降级链（R5）；
- **L2/L3 缓存是重排段的终极解法**：同一方案二次评审，L3 直接命中，重排一次都不跑。

全云 API 对照口径：检索段 < 300ms、重排段 300ms/评分项——云 API 用钱换 CPU，本地 Ollama 用 CPU 换钱，这是 04 文档的部署期决策，缓存对两个口径都成立。

## 命中率观测

trace 里记 `cache_hit: none|l1|l2|l3`（A8 埋点字段之一）。命中率是缓存好坏的唯一数字：

- L1 命中率低 → 查询文本不稳定（谁在拼不一样的 query_text？）
- L2 命中率低 → `doc_version` 粒度太细或方案老在变（业务现象，不是 bug）
- L3 命中率低 → `prompt_version` bump 太频繁（每次调 prompt 都全量失效，要有心理预期）

## 本阶段术语

> 【白话】**三级缓存**：查询向量（L1）→ 检索结果（L2）→ 最终结论（L3），一层比一层贵，一层比一层省得多。
> 【白话】**缓存键**：缓存内容的身份证。键里少一个维度（版本号），失效就不完整——拿旧数据当新数据用。
> 【白话】**TTL**：缓存存活时间。L1 一天、L2 一周、L3 跟随 prompt 版本。
> 【白话】**P95**：95 分位延迟——100 次里第 95 快那次的时间。比平均值更能代表"用户等待感受"。
> 【白话】**读失败当 miss**：缓存查不到就直查数据源。缓存的故障模式必须是"变慢"，不能是"变错"。

## 完成标准

- 单测（FakeCache）：①L2 键含 doc_version——换版本后 get 返回 None ②L3 键含 prompt_version——换版本后 get 返回 None ③`sha256_key("a", "bc")` != `sha256_key("ab", "c")`（分隔符歧义防御）
- 同一评分项连续两次检索：第二次 L1 命中，嵌入调用次数为 1（mock embed_fn 计数）
- 同一方案二次评审：L3 命中，LLM 调用次数为 0
- Redis 故障演练：kill redis 后检索照常返回正确结果（读失败当 miss 生效）
- trace 里 `cache_hit` 字段可见，且一次 L3 命中任务的 trace 显示重排 span 不存在
