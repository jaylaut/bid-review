# 代码生成自查清单（强制）

> **定位**：本文件是「生成代码前的强制自查清单」。**每次生成代码前，必须先完整阅读本文件**，逐条对照自查；生成完成后，再对照本文件逐条复核，确认没有复现清单中的任何问题。
>
> **来源**：2026-10-27 一次代码生成对话中暴露的问题，逐条归纳而成。凡本清单记录过的问题，后续一律不得重复出现。
>
> **配套纪律**：本清单与 `R0-契约与启动自检.md` §「config/rag.yaml：配置驱动」、`R1-解析与清洗.md` §「质量门」强相关，生成 RAG 相关代码时须一并阅读。

---

## 一、阈值 / 配置类错误（最高优先级）

### ⚠️ 1. 阈值硬编码进代码，违反「阈值进配置」铁律

- **错误现象**：`quality_gate.py` 里写了 `QUALITY_MIN_SCORE = 6`，与 `config/rag.yaml` 里的 `quality_gate.min_score: 6` 重复定义。
- **违反规范**：R0 文档明确「阈值全部进配置，不散落在代码里」——R7 阈值标定要改的就是 yaml 文件，硬编码在代码里则每次标定都是一次发版。
- **正确做法**：
  - 规则（算法逻辑）留代码，阈值（会调的数字）留 `config/rag.yaml`。
  - 阈值通过**函数参数注入**，不在模块内定义常量。
  - 调用方负责从配置读值并传入，函数本身不关心阈值从哪来。
- **同类隐患（务必一起检查）**：`sample_rate: 0.05`（抽检率）、`threshold: 0.8`（页眉页脚比例）、`0.85`（近重复 Jaccard）、`512 / 64 / 2000`（分块 token）、`0.15`（拒答阈值）——**凡是配置里已定义的数字，代码里一律不得再硬编码默认值**。

## 二、代码完整性问题

### ⚠️ 2. 缺 import

- **错误现象**：`check_parse_sync.py` 正文里用了 `json.load`，但顶部 import 列表漏写了 `import json`。
- **正确做法**：生成代码后，**通读一遍正文用到的每个模块 / 函数，逐一核对顶部 import**，做到「用了什么就导什么、导了什么就真用到」，不遗漏、不冗余。

---

## 三、与既有代码 / 契约冲突

### ⚠️ 3. 没先读既有代码就「重新发明」已存在的模块

- **错误现象**：生成 `parsers/`、`cleaning/` 的「注释版」，但这两个模块项目里**已经落地且逻辑正确**，属于重复劳动，还可能引入不一致。
- **正确做法**：生成前**先读对应目录的既有文件**，判断是「补齐缺失」还是「重写已有」；已有且正确的模块，只补注释、不重写逻辑。

### ⚠️ 4. 生成的功能与文档现状脱节

- **错误现象**：R1 文档当前状态标注「清洗模块已落地并单测全覆盖」，但仍把清洗模块当作「待实现」来生成完整代码。
- **正确做法**：生成前**先看文档头部「当前状态」**和「要建的文件」清单，只生成真正缺失的部分，已落地的只做引用说明。

---

## 四、风格与「每行一功能」要求

### ⚠️ 5. 注释里「并」进了额外代码说明，不够纯净

- **错误现象**：把「需要补 import json」写进了行内注释正文，而不是干净地在顶部导入。
- **正确做法**：注释只解释「这一行 / 这段在干什么、为什么」，**不把「要改的 TODO / 待办」混进注释**；待办事项单独在最终回复里说明。

---

## 五、边界与职责划分

### ⚠️ 6. 模块职责边界要分清「逻辑 vs 配置 vs 数据」

- **正确分工**：
  - 打分规则、算法 → `.py` 逻辑
  - 阈值、开关 → `config/rag.yaml`
  - 登记表内容 → `manifest.json`（数据文件）
- **教训**：`manifest.py`（读写代码）与 `manifest.json`（数据）是两个东西，生成时要讲清各自路径和职责，不能混为一谈。

### ⚠️ 7. 脚本 / 命令行工具用裸 `print` 输出，未走结构化日志

- **错误现象**：`check_parse_sync.py`（对账脚本）用 `print(...)` 打印对账结果，绕过了项目唯一的日志入口 `common/logging.py`。
- **违反规范**：`common/logging.py` 是全项目**唯一日志入口**（提供 `get_logger`、自动脱敏、trace_id 注入、异步落盘、可被 Alloy/Loki 采集）。对账脚本输出的「缺失文件」「命名冲突」正是最需要进日志系统、能被告警采集的内容（对应 R0 里 `reconcile.alert_threshold` 告警字段）。
- **正确做法**：
  - **脚本 / 命令行工具**的输出，凡需要被采集、告警、结构化检索的，一律用 `common.logging` 的 `get_logger` 打结构化日志（`log.info("事件名", 字段=值)`），不用裸 `print`。
  - **纯函数 / 库函数**不打日志，由调用方打——这是合理惯例，不是疏漏。
- **判断标准**：凡是"跑在管道里、结果需要被监控告警"的代码（脚本、worker、ingest），走日志；凡是"被 import 后当工具函数用"的代码，不打日志。

## 六、生成后自查 7 问（逐条过）

生成任何代码后，先回答这 7 个问题：

1. **阈值**：这段代码里有没有硬编码的配置值？有 → 改成参数注入，值留给 `config/rag.yaml`。
2. **import**：正文用到的库，顶部都导入了吗？有没有多余的 import？
3. **是否已存在**：这个模块 / 函数项目里是不是已经有了？有 → 只补注释不重写。
4. **是否真缺失**：对照文档「当前状态」和「要建的文件」，这段代码是不是真的要新建？
5. **注释纯净**：注释只讲原理，没把 TODO、改动说明混进去？
6. **职责清晰**：逻辑 / 配置 / 数据三者的边界划清了吗？
7. **日志规范**：脚本 / worker / ingest 的输出走 `common.logging` 的 `get_logger` 了吗？还是用了裸 `print`？

## 附：质量门「6 分」阈值的出处说明（避免再次误解）

- **结论**：`min_score: 6` 与「0–8 分」的出处是**电子书《从零搭建生产级 RAG 平台》4.6 节**（见 `03-RAG子系统详细架构.md` §3.1 注释、R1 §质量门），**不是本项目从数据标定出来的**。
- **现状**：该值属于「沿用电子书推荐值」的初始值，**尚未经本项目真实数据标定**。`config/rag.yaml` 第 6 行注释里已有人留了疑问「能否调高？」——说明该阈值仍待定。
- **正确对待方式**：把它当**可调配置项**（已在 yaml），后续 R7 评测阶段用真实标书数据标定；代码里不得再出现第二个硬编码的 6。
