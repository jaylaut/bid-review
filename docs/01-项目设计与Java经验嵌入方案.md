# 招投标技术方案评审系统 —— 项目设计与 Java 经验嵌入方案

> 定位：不是"AI 评审 demo"，而是"能进国企/招标代理机构生产环境的 AI 评审系统"。
> 核心命题：**Python 负责判断，Java 负责管住判断。**

---

## 一、先诚实回答：Java 经验到底体现在哪

分三层，强度递增。

### 第一层（弱）：AI 核心链路里，Java 基本没有位置

RAG 检索、Agent 编排、分块、Prompt、评估、向量检索 —— Python 生态压倒性领先。
如果用 Java 硬写这一层，是在给自己加难度且没有生态支撑（Java 侧虽有 LangChain4j / Spring AI，但本项目定位底层理解、一律不用，Python 侧也全程手写不用 LangChain/LangGraph）。

**结论：这一层不要用 Java，用了是减分。**

### 第二层（强）：让"评审引擎"变成"能进企业的系统"，全是 Java 的主场

这一层才是 16 年经验的真实落点，具体 6 项：

| # | Java 侧能力 | 在招投标场景的具体问题 | 为什么纯 Python 团队做不好 |
|---|---|---|---|
| 1 | **异步长任务编排** | 一份 300 页招标文件，解析+抽取+比对需 3–8 分钟。必须：提交即返回 taskId、进度推送、可取消、失败重试、断点续传 | 只会写同步阻塞脚本，一上量就超时、OOM、无法续跑 |
| 2 | **权限与数据隔离** | 代理机构代办多项目、投标方只能看自己方案、专家只能看分配标段、敏感项目物理隔离 | **权限必须在检索层生效**（检索前过滤），不能只在前端挡。这是 RAG 权限设计的核心难点，也是绝大多数 demo 的死穴 |
| 3 | **审计与全链路留痕** | 评标是受监管行为，可能被质疑/投诉/审计。要记录：谁提交、模型版本、检索了哪些片段、AI 给了什么结论、人工改成什么、改的理由 | 没人做。而不做审计，系统进不了国企和政府采购 |
| 4 | **与存量系统集成** | 客户的招投标平台/OA/档案系统基本都是 Java + Oracle/达梦，信创环境（麒麟 OS、东方通、国密） | 纯 Python 团队啃不动信创适配和存量集成 |
| 5 | **文档解析与回写保真** | 输入是几百页 docx/pdf（合并单元格大表格、多级编号、扫描件）；输出必须是格式规范的 **Word 技术偏离表** | Java 的 Apache POI 对 docx 的 XML 层控制力强于 python-docx（表格合并、样式、修订痕迹）；PDFBox/Tika 生态成熟 |
| 6 | **稳定性与成本治理** | 大模型 API 有 RPM/TPM 限制，多项目并发要排队；要熔断、降级兜底、Token 配额与成本核算、解析结果缓存 | demo 阶段完全不会遇到，一上生产全是坑 |

### 第三层（最强，是岗位定位）

招投标行业的客户买的不是"一个模型"，而是**"一套能过等保、能过审计、能接进现有平台、能私有化部署的系统"**。

所以你的岗位定位应该是：
> **AI 应用架构师 / AI 落地负责人**，而不是 "AI 算法工程师" 或 "Python 工程师"。

这正是 16 年企业级 Java + 6 年带团队最值钱的地方 —— 而这个行业里，同时具备"懂 AI 应用"和"懂企业级工程"的人极少。

## 二、双栈架构与职责边界

```
[前端 / 存量招投标平台 / OA]
        │ HTTP：提交评审任务，返回 taskId
        ▼
┌─────────────────────────────────────────────────┐
│  review-platform   （Java / Spring Boot）        │
│  ── 管住判断 ──                                  │
│  · 任务编排 / 状态机 / 断点续传 / 失败补偿        │
│  · RBAC + 行级数据权限（检索前过滤的入参来源）    │
│  · 审计留痕 / 全链路回放                          │
│  · 文件管理（对象存储）/ 版本管理                  │
│  · Word 成文：技术偏离表（Apache POI）            │
│  · 限流 / 配额 / Token 成本核算 / 缓存            │
└──────────────────┬──────────────────────────────┘
                   │ 内部 REST（JSON Schema 强契约）
                   ▼
┌─────────────────────────────────────────────────┐
│  review-engine     （Python / FastAPI）          │
│  ── 负责判断 ──                                  │
│  · 文档解析（PyMuPDF / unstructured）             │
│  · 评分项抽取（结构化输出 + schema 校验）         │
│  · RAG 检索（BM25 + 向量 + Rerank）              │
│  · 逐项比对 / 偏离判定（Agent 多步）              │
│  · 段落级引用定位                                 │
│  · 置信度 + 拒答                                  │
└──────────────────┬──────────────────────────────┘
                   ▼
        [向量库 / 全文索引]   [LLM API 或本地模型]
```

### 边界为什么这么切（这是面试要讲的重点）

1. **变化频率不同**：模型和 Prompt 半年一换，企业业务系统要稳定五年。切在两个生命周期不同的层之间，模型迭代不会震到业务系统。
2. **能力属性不同**：判断是概率性的，必须带置信度和拒答；管理是确定性的，必须可审计、可重放。
3. **可替换性**：AI 引擎可整体替换（换成通义/DeepSeek/本地模型），Java 侧零改动。这是甲方最关心的事。

## 三、关键契约：AI 引擎的输出必须长什么样

这是整个设计的技术核心。**AI 引擎绝不能只返回一段文本**，必须返回带置信度、引用、拒答的结构化结果：

```json
{
  "task_id": "evt-2026-1021-0001",
  "scoring_item_id": "S3.2.4",
  "item_text": "支持国产数据库（达梦、人大金仓）适配",
  "verdict": "PARTIAL",
  "confidence": 0.72,
  "evidence": [
    {
      "doc": "投标文件-技术部分.docx",
      "page": 87,
      "section": "5.3.2 数据库兼容性",
      "text": "……已完成达梦 DM8 的适配测试……",
      "bbox": [120, 340, 520, 372]
    }
  ],
  "reason": "仅提及达梦，未提及人大金仓；且未提供适配验证报告",
  "missing_aspects": ["人大金仓适配", "适配验证报告"],
  "needs_human": true,
  "engine": { "model": "xxx", "prompt_version": "v0.7", "index_version": "idx-20261020" }
}
```

Java 侧据此决策：

| 条件 | Java 侧动作 |
|---|---|
| `confidence >= 0.9` 且 `verdict in (PASS, FAIL)` | 自动采纳，标记"AI 判定" |
| `0.6 <= confidence < 0.9` 或 `PARTIAL` | 进入人工复核队列，预填建议 |
| `confidence < 0.6` 或 `needs_human=true` | 强制人工判定，AI 仅提供线索 |
| `verdict = NOT_FOUND` | 提示"未在方案中找到对应内容"，要求人工确认是否真缺失 |

**这套"置信度驱动的人机分流"就是企业级 HITL（Human-in-the-Loop，关键判断保留人工介入）的工程化表达** —— 比"AI 全自动评审"高级得多，也安全得多。这一条讲出来，面试官立刻知道你懂落地。

## 四、如果只做 Python Demo，会死在哪（自检清单）

- 提交后浏览器转圈 5 分钟，超时白屏 → 没有异步任务
- 换个项目就要改代码里的路径和参数 → 没有任务抽象
- 所有用户看到同样的检索结果 → 没有权限过滤，**泄露他人投标方案（这在招投标里是重大事故）**
- 出了问题无法解释"AI 为什么这么判" → 没有留痕和回放
- 输出是一段 Markdown，专家没法直接用 → 没有 Word 成文
- 并发两个人用就报 API 限流 → 没有队列与限流
- 面试官问"这个能卖给招标代理机构吗" → 答不上来

**上面每一条，都是你 Java 经验可以正面回答的问题。**

## 五、8 周执行计划（双栈）

### Phase 0：数据与评估集（第 1 周，先做这个）

- [ ] 从中国政府采购网 / 省级公共资源交易中心 / 中国招标投标公共服务平台，下载 10–15 套公开招标文件（技术需求书 + 评分办法）
- [ ] 收集 3–5 份公开的投标技术方案（或基于招标文件自行编写模拟方案）
- [ ] 从评分办法中整理出 **80–120 个评分项**，人工标注每个评分项在投标方案中的"应答位置 + 判定（完全响应/部分响应/未响应/负偏离）"
- [ ] 产出 `eval/golden_set.jsonl`，字段与第三节契约对齐
- [ ] **验收：能自动跑出"评分项覆盖率"和"判定准确率"两个数字**

> 这一步过不了，项目不要继续。评估集是立项门槛，不是后期工作。

### Phase 1：Python 引擎最小闭环（第 2 周）

- [ ] PDF/docx 解析 → 保留页码、章节号、段落 ID（**引用定位的基础**）
- [ ] 评分项抽取（结构化输出 + Pydantic 校验）
- [ ] 朴素检索（定长切分 + 向量 top-k）
- [ ] 逐项判定 → 输出第三节契约 JSON
- [ ] **验收：跑通 golden set，得到基线准确率（预计 45–60%），记录在案**

### Phase 2：RAG 升级（第 3 周）

- [ ] 按章节层级递归切分 + 父子块
- [ ] 混合检索（手写 BM25 + 向量 + RRF 融合）
- [ ] Rerank（Qwen3-Reranker，Ollama + logprobs 打分）
- [ ] 查询改写（用评分项文本生成检索查询）
- [ ] 引用定位精确到段落
- [ ] **验收：准确率对比表（基线 → +混合检索 → +Rerank → +改写），每项增益单独可测**

### Phase 3：Agent 化（第 4 周）

- [ ] Agent 主循环（手写：工具注册 + 分发 + 终止条件 + 步数/成本上限）
- [ ] 工具集：
  - `search_in_bid(query, filters)` —— 在投标方案中检索
  - `get_section(doc, section_id)` —— 取整节内容（跨块上下文）
  - `check_required_doc(item_id)` —— 检查是否有要求的证明材料
  - `compare_clause(item, candidate_text)` —— 单条精细比对
- [ ] 多步推理：先粗检索定位 → 判断是否需展开整节 → 是否需再查证明材料 → 出结论
- [ ] 置信度计算 + 拒答策略
- [ ] **验收：难例（跨章节、需看附件、负偏离）的判定准确率提升**

### Phase 4：Java 平台层（第 5–6 周）

- [ ] Spring Boot 骨架：任务提交 / 状态查询 / 进度 SSE / 取消 / 重试
- [ ] 任务状态机：`PENDING → PARSING → EXTRACTING → REVIEWING → DONE / FAILED`，支持断点续传
- [ ] RBAC + 行级权限：用户 → 项目 → 标段 → 文档；权限作为检索过滤条件透传给引擎
- [ ] 审计表：`audit_log(task_id, actor, action, model_version, evidence_ids, before, after, reason, ts)`
- [ ] Word 成文（Apache POI）：技术偏离表，含评分项、判定、依据页码、备注；样式规范化
- [ ] 限流/配额：按项目计算 Token 成本，超限排队
- [ ] **验收：两个不同项目并发跑，数据互不可见，各自有完整审计链路**

### Phase 5：部署与工程化（第 7 周）

- [ ] Docker Compose 一键起：platform + engine + 向量库 + 对象存储
- [ ] 可观测：Langfuse/LangSmith 做 trace，引擎每步落库
- [ ] 成本看板：每个评分项的平均 Token 与耗时
- [ ] 降级：LLM 不可用时的降级路径（返回 NOT_FOUND + 强制人工）
- [ ] **验收：能演示"模型超时 → 任务不丢 → 恢复后继续"**

### Phase 6：作品化（第 8 周）

- [ ] 3 篇技术博客：
  1. 《我把评分项判定准确率从 X 提到 Y，每一步的增益数据》
  2. 《为什么 AI 评审必须在检索层做权限过滤》
  3. 《Python 判断 + Java 管控：AI 应用的双栈边界怎么切》
- [ ] README 含架构图、评估结果表、演示 GIF
- [ ] 简历表述对齐（见第七节）

## 六、技术选型（2026 现状，明确排除过时方案）

| 层 | 选型 | 说明 |
|---|---|---|
| LLM | DeepSeek / 通义千问（API）；本地部署用 vLLM + Qwen | 不用太小的模型，长文档比对需要强模型 |
| 编排 | 手写 Agent 循环 + 自研 checkpointer/interrupt（**不用 LangGraph/LangChain**） | 底层理解优先，机制全部手写 |
| 检索 | BM25（自写）+ 向量 + RRF + Qwen3-Reranker（Ollama + logprobs） | **禁止 naive RAG**（纯向量 top-k 已淘汰） |
| 向量库 | 先用 numpy 暴力（<5万块够用）→ pgvector / Milvus | 先理解再上规模方案 |

> **版本对齐（2026-10-21 更新 10-22）**：本表的「numpy 暴力检索」「手写 BM25」属于**手搓学习期**（第二部分 L0–L3 的学习路线，目的是理解"向量检索=矩阵乘法、BM25=词频统计"）；**项目实现期的权威技术栈以 `02-系统总体架构与技术选型.md` 与 `03-RAG子系统详细架构.md` 为准**——从第一天直接用 pgvector + zhparser + Ollama（qwen3-embedding 嵌入 / Qwen3-Reranker 重排，logprobs 打分）。两者不冲突：手搓期在独立练习仓库完成，项目仓库走生产选型。
| 文档解析 | **MinerU**（统一解析：VLM 模式处理扫描件/图片型、pipeline 模式处理文本型/复杂中文；内置 PaddleOCR 兜底） | 以 `02-系统总体架构与技术选型.md` / `03-RAG子系统详细架构.md` §4.1 为准；评分办法表格由 MinerU 整表抽取后单独走结构化抽取 |
| 结构化输出 | Pydantic + JSON Schema 强约束 | 禁止让模型自由输出文本 |
| 平台层 | Spring Boot 3.x + MyBatis-Plus + PostgreSQL/达梦 + MinIO | 达梦用于演示信创适配 |
| 文档成文 | Apache POI（XWPF） | 表格合并、样式控制优于 python-docx |
| 可观测 | Langfuse（自托管） | 引擎 trace + 每步落库 |
| 评估 | 自建 golden set + 脚本 | 别用 Ragas 一把梭，合同/标书场景指标要自己定义 |

**明确不碰**：微调（先用 RAG + Prompt 解决）、多智能体框架全家桶、通用 Agent 平台、任何"一键生成"的低代码方案、**LangChain/LangGraph/LlamaIndex（高层 RAG/Agent 框架）、litellm（LLM 客户端抽象）、Spring AI（Java 侧 AI 框架）**——定位是底层理解，核心链路全部手写。

## 七、简历与面试表达

### 简历条目写法

> **招投标技术方案智能评审系统**（个人项目，2026.XX–2026.XX）
> - 设计 **Python 评审引擎 + Java 管控平台** 双栈架构，明确"判断"与"管控"职责边界，模型可整体替换而业务层零改动
> - 构建 120 项评分项标注评估集，评审判定准确率从基线 52% 提升至 81%（混合检索 +12%、Rerank +9%、查询改写 +8%，逐项增益可测）
> - 实现**检索层行级权限过滤**，确保投标方方案在向量召回阶段即被隔离，规避跨项目数据泄露
> - 实现置信度驱动的人机分流（≥0.9 自动采纳 / 0.6–0.9 人工复核 / <0.6 强制人工），全链路审计可回放
> - Java 侧基于 Apache POI 自动生成规范技术偏离表；异步任务支持断点续传与失败补偿

### 面试金句

> "我不是做了个 AI demo。我把它做成了一套能进招标代理机构的系统：**AI 负责判断，Java 负责权限、审计、任务和成文**。模型从 DeepSeek 换成通义，我的业务系统一行代码都不用改 —— 这是甲方最在意的事。"

### 面试官最可能追问的 5 个问题（提前准备）

1. 你怎么保证不泄露 A 投标方的方案给 B 投标方？（→ 检索层过滤 + 向量分区）
2. 评分项判错了谁负责？（→ 置信度分流 + 全量留痕 + 人工终审）
3. AI 说"未响应"，但方案里其实写了，怎么办？（→ 证据引用必须是可点击的原文片段；NOT_FOUND 一律人工确认）
4. 为什么不全用 Python 或全用 Java？（→ 变化频率 / 能力属性 / 可替换性三条理由）
5. 这个和市面上已有的评审工具差在哪？（→ 你的是"可嵌入存量系统 + 可审计 + 可私有化"的底座，不是又一个 SaaS）

## 八、差异化定位（一句话）

市场上做招投标 AI 的，要么是**只会调模型的**（进不了企业），要么是**只会做系统的**（不懂 AI）。

你的位置是**中间那条缝**：能把 AI 判断能力，以企业级工程的方式，安全地嵌进一个受监管、要走信创、要过审计的业务系统里。

**这个位置目前供给极少，而它恰好是 16 年 Java 经验唯一能形成差异化优势的地方。**
