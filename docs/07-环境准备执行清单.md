# 环境准备执行清单（Agent 开发前置）

> **适用**：Windows 10/11 + Git Bash，本机首次搭建 `review-engine` 开发环境。
> **目标**：从零到"能 import 全部依赖 + 中间件全部健康 + 自检脚本全绿"，之后才开始写 A0 契约。
> **总耗时**：顺利 20 分钟；含首次编译 PG 镜像约 35 分钟；网络不畅另计。
> **原则**：每一步都有验证命令，**验证不过不要往下走**——后面所有报错都会变成"到底是环境问题还是代码问题"的猜谜。

## 二、逐步执行

### 第 1 步 · 启动 Docker Desktop

**为什么**：Docker CLI 装了不等于能用。现在 `docker info` 报的是"找不到 npipe"，说明**引擎进程没起来**，只是命令行工具在。

```bash
# 启动（GUI 程序，也可以直接从开始菜单点）
"/c/Program Files/Docker/Docker/Docker Desktop.exe" &
```

**验证**（等到输出里出现 `ServerVersion` 才算好，通常 30–60 秒）：

```bash
docker info --format 'engine={{.ServerVersion}} os={{.OSType}} mem={{.MemTotal}}'
```

期望：`engine=29.7.2 os=linux mem=...`。如果还是报 npipe 错误，去任务栏看鲸鱼图标是否在转圈，等它变成稳定状态。

> 【白话】**镜像 vs 容器**：镜像是"装好系统的光盘模板"（只读），容器是"用这张光盘启动起来的一台机器"（可读写）。`docker compose up` 做的是"按配方建光盘、再开机"。
> 【白话】**volume（数据卷）**：容器的"外接硬盘"。容器删了重建，卷里的数据还在。所以下面改了 compose 配置重启，数据库里的表不会丢。

**首次使用建议**：Docker Desktop → Settings → Resources，内存给到 **6–8GB**。本项目 4 个中间件约 4.5GB（见 `docs/02 §七`），给太少会随机 OOM。

---

### 第 2 步 · 安装 uv

**为什么用 uv**：`docs/02 §4.4` 定的运行时是 "Python 3.12 + uv + ruff + pytest"。uv 一个工具同时干三件事：管 Python 版本、建虚拟环境、装依赖（比 pip 快一个数量级）。

> 【白话】**虚拟环境（venv）**：给这个项目单独的"工具箱"。项目 A 要 pydantic 2.8、项目 B 要 2.5，各自装在各自箱子里，互不打架。不建虚拟环境就是全机共用一个工具箱，迟早冲突。
> 【白话】**uv.lock**：依赖的"精确配方快照"。`pyproject.toml` 说"要 pydantic ≥2.8"，`uv.lock` 记的是"实际装的是 2.9.1，连它依赖的 12 个包的版本一起记下来"。别人拿到仓库能装出**完全一样**的环境。

三选一，按你习惯：

```bash
# 方式 A：官方脚本（推荐，装到 ~/.local/bin）
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"

# 方式 B：winget
winget install --id=astral-sh.uv -e

# 方式 C：已有 pip，用它装（最慢但最稳）
py -3.12 -m pip install --user uv
```

**验证**（**装完必须新开一个终端**，否则 PATH 没刷新）：

```bash
uv --version
```

期望：`uv 0.x.x`。

> ⚠️ 如果报 `command not found`，90% 是没重开终端。手动确认一下：
> ```bash
> ls ~/.local/bin/uv.exe && export PATH="$HOME/.local/bin:$PATH"
> ```

### 第 3 步 · 确认 Python 3.12

**为什么锁定 3.12**：`docs/02 §4.4` 明确 3.12。你这台机器默认 `python` 是 3.13，直接用它建环境会踩两个坑：一是部分依赖的预编译 wheel 还没跟上 3.13，会退化成源码编译（Windows 上需要 MSVC，很容易失败）；二是 `asyncpg` 在 3.13 早期版本上有兼容问题。

```bash
# 看 uv 能识别到哪些 Python
uv python list

# 如果列表里没有 3.12.x，让 uv 自己装一个（约 100MB）
uv python install 3.12
```

**验证**：

```bash
uv python find 3.12
```

期望：输出一个 `python.exe` 的绝对路径（你机器上应该是 `E:\CodingTools\python3.12\python.exe` 或 uv 自己管理的路径）。

> 【白话】**wheel（.whl）**：Python 包的"预编译安装包"。有 wheel 就是解压即用；没有 wheel 就得在你机器上现场编译，还得先装编译器。所以"版本别太新"能省掉大量环境问题。

### 第 4 步 · 建虚拟环境 + 安装依赖

```bash
cd /e/project/bid-review/review-engine

# 建环境（会生成 review-engine/.venv）
uv venv --python 3.12

# 装依赖（含 dev 组：pytest / ruff / respx / mypy）
uv sync
```

> 【白话】**`uv sync` 在干什么**：读 `pyproject.toml` 的依赖列表 → 算出所有需要装的包（含间接依赖）→ 写进 `uv.lock` → 下载安装到 `.venv`。它保证"当前环境 = 配置文件描述的状态"，多装的会删、少装的会补。

**验证（这一步最关键，必须全部 import 成功）**：

```bash
uv run python -c "
import fastapi, pydantic, sqlalchemy, asyncpg, pgvector, httpx, tenacity
import aio_pika, redis, mcp, structlog, orjson
import opentelemetry.sdk
print('deps ok | pydantic', pydantic.VERSION, '| sqlalchemy', sqlalchemy.__version__)
"
```

期望：`deps ok | pydantic 2.x | sqlalchemy 2.x`

**同时验证工程链**：

```bash
uv run ruff --version
uv run pytest --version
```

**装了什么、为什么装**（出问题时知道该怀疑谁）：

| 包 | 用途 | 对应文档 |
| --- | --- | --- |
| `fastapi` + `uvicorn` | 同步查询接口（评审追问、健康检查） | 02 §4.4 |
| `pydantic` + `pydantic-settings` | 契约强制校验、`.env` 加载 | 03 §5.6、07 §A0 |
| `sqlalchemy[asyncio]` + `asyncpg` | 异步访问 PG（同步驱动会阻塞事件循环） | 02 §4.4 |
| `pgvector` | Python 侧注册 `vector` 类型的编解码 | 03 §3.2 |

| `grpcio` + `grpcio-tools` + `protobuf` | **自研** RocketMQ gRPC 客户端（官方 SDK 依赖 C++ 在 Windows 装不上） | 02 §4.3 |
| `redis[hiredis]` | L1–L3 缓存、取消标记 | 03 §六 |
| `mcp` | 四个工具暴露成 MCP server | 02 §4.4 |
| `opentelemetry-*` | trace 全链路透传 | 02 §五 |
| `structlog` + `orjson` | 结构化日志、状态序列化提速 | —— |
| `pytest` + `pytest-asyncio` + `respx` | 测试 + mock httpx（不联网测 LLM 客户端） | 07 §A0 |
| `ruff` + `mypy` | 格式化/lint/类型检查 | 02 §4.4 |

#### 明确**不要**装（这是铁律，不是偏好）

```bash
# ❌ 一行都不要执行
# pip install langchain langgraph llama-index litellm openai sentence-transformers torch
```

| 禁止 | 原因（`docs/02 §十一`、`docs/README` 约定） |
| --- | --- |
| `langchain` / `langgraph` / `llama-index` | 项目定位是**底层理解**。Agent 循环、checkpointer、interrupt 全部手写，用框架等于把这些机制藏进黑盒 |
| `litellm` | 它把"发 HTTP、解析流式、多 provider 路由"藏起来了，而这正是要自己写一遍的东西 |
| `openai` SDK | 同上，判定 LLM 客户端要用 `httpx` 手写（OpenAI 兼容接口） |
| `sentence-transformers` / `torch` | 嵌入走 Ollama 的 HTTP 接口，本地不需要跑推理框架（省 2GB+ 依赖） |
| `celery` | 编排权在 Java 侧，Python worker 只做无状态执行 |

> 【白话】**为什么这里"少装"比"多装"重要**：装上 langchain 你会忍不住用它，然后就再也说不清"检索链路每一步发生了什么"——而这条链路的每一步恰好是这个项目唯一的价值。这也是为什么 `docs/02 §十一` 专门列了一张"明确排除"清单。

### 第 5 步 · 构建并启动中间件

**这一步耗时最长**，因为要现场编译中文分词扩展。

```bash
cd /e/project/bid-review/deploy

# 首次：构建自建 PG 镜像（pgvector + zhparser）
docker compose build postgres

# 起全部 4 个服务
docker compose up -d

# 看状态（等 postgres 变成 healthy）
docker compose ps
```

**为什么要自建 PG 镜像**：`docs/03 §3.2` 的 DDL 里用了 `to_tsvector('zh', content)`，这个 `zh` 配置由 **zhparser** 提供。官方 `pgvector/pgvector` 镜像**不含** zhparser，必须自己编译 SCWS + zhparser（`docs/05 §四.3` 把这项列为"环境落地的第一个硬任务"）。

> 【白话】**pgvector**：让 PostgreSQL 能存"向量"（一串小数）并按相似度排序的扩展。它的作用相当于给数据库装了个"语义相似度搜索引擎"。
> 【白话】**zhparser / SCWS**：中文分词器。英文按空格切词就行，中文"达梦数据库"必须切成"达梦 / 数据库"才能做关键词检索。SCWS 是底层词库，zhparser 是 PG 的适配层。
> 【白话】**HNSW**：向量索引的一种，原理类似"高速公路分层导航"——先走粗粒度的高速路快速接近目标区域，再走小路精确定位。没有它，每次查询都要把全表向量算一遍（全表扫），而且**不会有任何报错**，只是慢得莫名其妙。

**验证一：四个容器都起来了**

```bash
docker compose ps --format "table {{.Name}}\t{{.Status}}"
```

期望四行，postgres 显示 `Up (healthy)`。

**验证二：两个扩展都装上了**（这是本步的核心验收）

```bash
docker exec -it bid-pg psql -U bid -d bid_review -c "
SELECT extname, extversion FROM pg_extension WHERE extname IN ('vector','zhparser');
"
```

期望：
```
 extname  | extversion
----------+------------
 vector   | 0.8.x
 zhparser | 2.2
```

**验证三：中文分词真的在工作**

```bash
docker exec -it bid-pg psql -U bid -d bid_review -c "
SELECT to_tsvector('zh', '支持国产数据库达梦DM8适配');
"
```

期望：输出类似 `'dm8':5 '中国':2 '国产':3 '数据库':4 '支持':1 '达梦':6 '适配':7`（分词结果，不是一长串原文）。**如果这里报"text search configuration zh does not exist"，说明 init 脚本没跑**——见故障 5。

**验证四：管理台能打开**

- RocketMQ：无内置 Web 管理台（可用 `E:\CodingTools\rocketmq-dashboard-1.0.0`，默认 http://localhost:8080）
- MinIO：http://localhost:9001 （`minioadmin` / `minioadmin123`，凭证在 `deploy/minio/.env`）

**关于建表**：本步**不建业务表**。`documents / chunks / scoring_items` 的 DDL 在 `docs/03 §三`，`agent_state` 在 `docs/10 §A4`，到对应阶段再执行。现在自检脚本会提示"chunks 表尚未创建"，属于**预期内的 WARN**。

### 第 6 步 · 验证 Ollama（不用下载）

两个核心模型你已经有了，只验证接口可用即可：

```bash
# 确认模型在位
ollama list | grep -E "qwen3-embedding|Qwen3-Reranker"

# 确认服务在跑
curl -s http://localhost:11434/api/version
```

期望：能看到两个模型各 639MB，以及 `{"version":"0.30.5"}`。

真正的接口级验证（维度是不是 1024、有没有归一化、logprobs 能不能用）由第 8 步的自检脚本完成，这里不用手敲。

> 【白话】**嵌入（embedding）**：把一段文字变成一串数字（本项目是 1024 个小数）。语义相近的文字，这串数字也接近。检索就是"算两串数字有多接近"。
> 【白话】**重排（rerank）**：先粗筛出 20 个候选，再让一个更精细的模型逐个判断"这段文字到底有没有回答问题"。本项目用它打分，分数低于 0.15 就判"方案没写"——所以它输出的**必须是连续分数**，不能只是"是/否"两个字。
> 【白话】**logprobs**：模型对每个候选词的"把握程度"。Qwen3-Reranker 只会吐 "yes" 或 "no"，但通过 logprobs 能拿到"yes 的概率是 0.93"，这才是可用的连续分数。拿不到 logprobs，拒答阈值就失效（`docs/03 §5.4`）。

### 第 7 步 · 配置 `.env`

```bash
cd /e/project/bid-review/review-engine
cp .env.example .env
```

然后**只需要改一处**——填 LLM 的 API Key：

```bash
# 用你习惯的编辑器打开
code .env      # 或 notepad .env
```

找到这段，把 key 填上：

```ini
LLM_PROVIDER=deepseek
LLM_BASE_URL=https://api.deepseek.com
LLM_API_KEY=sk-你的真实key
LLM_MODEL=deepseek-chat
```

> 【白话】**`.env` 是什么**：一份"密码本"，把密钥、端口这些不该写进代码的东西单独放。`.env` 必须进 `.gitignore`（模板文件 `.env.example` 才是提交的那份）。
> 【白话】**DSN**：数据库连接串，格式是 `驱动://用户:密码@主机:端口/库名`。注意本项目**必须**用 `postgresql+asyncpg://` 前缀，用 `postgresql://` 会走同步驱动，协程里直接报错。

**如果你暂时没有 API Key**：先跳过，自检会报一条 FAIL，但不影响 A0/A1 阶段写契约和跑假 LLM。等要跑真实判定时再填。

### 第 8 步 · 跑环境自检

这是**唯一的总验收口**，一次把所有坑都探出来。

```bash
cd /e/project/bid-review/review-engine
uv run python ../scripts/check_env.py
```

期望输出：

```
══════════════════════════════════════════════════════════════════════════
                                 环境自检报告
══════════════════════════════════════════════════════════════════════════
[ OK ] Python 版本            3.12.10
[ OK ] 判定 LLM               deepseek / deepseek-chat · key 已配置
[ OK ] PG 连接                PostgreSQL 16.x
[ OK ] pgvector 扩展          v0.8.x
[ OK ] zh 分词配置            v2.2 · 'dm8':5 '中国':2 '国产':3 ...
[WARN] HNSW 索引              chunks 表尚未创建（建表见 docs/03 §3.2），本项跳过
[ OK ] Ollama 嵌入            qwen3-embedding:0.6b · 1024 维 · 已归一化
[ OK ] Ollama 重排            dengcao/Qwen3-Reranker-0.6B:Q8_0 · logprobs 可用
[ OK ] Redis                  PING → True
[ OK ] RocketMQ               proxy gRPC localhost:8081 可连
[ OK ] MinIO                  http://localhost:9000 健康
──────────────────────────────────────────────────────────────────────────
 ✓ 全部通过（1 项警告不影响开发）
```

脚本检查的正是 `docs/03 §九` 定义的 **fail-fast 七项**，外加 Redis / MQ / MinIO：

| 检查项 | 为什么必须 fail-fast |
| --- | --- |
| Python 版本 | 版本错会导致部分依赖退化成源码编译，一路报奇怪的错 |
| PG 连接 | 连不上，后面全是"模块加载失败"的假象 |
| pgvector 扩展 | 没装 → `vector` 类型不存在，DDL 直接失败 |
| zhparser + zh 配置 | 没装 → 中文全文检索静默退化成"按空格切词"，中文根本切不开，**且不报错** |
| **向量维度 1024** | 维度不一致 → 插入时报错，或者更糟：能插但检索结果全是垃圾 |
| **向量已归一化** | 没归一化却用内积索引 → 相似度算错，检索"看起来在跑但结果不对" |
| **HNSW 索引存在** | 不存在 → 全表扫，**没有任何警告**，只是慢；这是 pgvector 最经典的静默失败 |
| **重排 logprobs 可用** | 拿不到 → 拒答阈值失效，"未响应"判不出来，等于最核心的评审能力没了 |

> 【白话】**fail-fast**：启动时就把所有"配置错了但不会报错"的点检查一遍，不合格直接不让跑。上面标粗的四项都是**静默失败**——不会崩，但结果是错的。这种错误在生产上最难查，所以必须在开机前拦掉。

## 三、验收清单（全部打勾才能开始写 A0）

## 四、常见故障对照表

| # | 现象 | 原因 | 处理 |
| --- | --- | --- | --- |
| 1 | `uv: command not found` | 装完没重开终端，PATH 未刷新 | 新开终端；或 `export PATH="$HOME/.local/bin:$PATH"` |
| 2 | `docker: cannot connect to the Docker API ... npipe` | Docker Desktop 引擎没启动 | 启动 Docker Desktop，等鲸鱼图标稳定 |
| 3 | `Bind for 0.0.0.0:5432 failed: port is already allocated` | 本机已装 PostgreSQL 并占用 5432 | 改 `docker-compose.yaml` 里映射为 `"15432:5432"`，同时改 `.env` 的 `PG_DSN` 端口 |
| 4 | `docker compose build postgres` 卡在 `wget github.com` | 国内网络拉 GitHub 源码超时 | 改 `deploy/postgres/Dockerfile` 的 `ZHPARSER_URL` 为 gitee 镜像，或先把源码包放进 `deploy/postgres/` 改用 `COPY` |
| 5 | `text search configuration "zh" does not exist` | init 脚本只在**数据卷为空**时执行；之前起过一次就会跳过 | `docker compose down -v`（**会清库**）再 `up -d`；或手动执行 `01-extensions.sql` |
| 6 | `CREATE EXTENSION zhparser` 报找不到 | 用了官方 `pgvector/pgvector` 镜像，不是自建的 | 确认 compose 里是 `build:` 而不是直接 `image:`，先 `build` 再 `up` |
| 7 | `asyncpg` 报 `ProactorEventLoop does not support add_reader` | Windows 默认事件循环不兼容 asyncpg | 代码入口加 `asyncio.set_event_loop_policy(asyncio.WindowsSelectorEventLoopPolicy())`（自检脚本已内置） |
| 8 | `uv sync` 报版本冲突 | 缓存了旧的解析结果 | 删 `uv.lock` 后重跑；仍不行加 `--refresh` |
| 9 | 嵌入维度返回不是 1024 | 模型名写错（比如用了 `bge-m3`） | 确认 `EMBEDDING_MODEL=qwen3-embedding:0.6b` |
| 10 | 重排 `logprobs` 为空 | Ollama 版本过低或模型不支持 logprobs | 升级 Ollama；或按 `docs/04 §六` 检查 `raw` + `logprobs` 参数与 chat template |
| 11 | MinIO 健康检查失败 | 镜像里 `mc` 命令或路径差异 | 该项是 WARN，可忽略；用浏览器开 9001 确认即可 |
| 12 | 磁盘突然少了几 GB | PG/Redis/MQ/MinIO 的 volume + 两个 639MB 模型 + uv 缓存 | `docker system df` 看占用；清理用 `docker compose down`（保留卷）而非 `-v` |

## 五、两个不用现在做、但要知道的事

**1. `OLLAMA_NUM_PARALLEL`**
A7 阶段会做 80 项并发，其中本地重排是 CPU 单实例，是最容易被忽略的瓶颈（`docs/10 §A7` 坑 1）。到时候可能需要调 Ollama 的并发参数。现在不用管，先记着有这个地方。

**2. `num_ctx` 必须显式设置**
`docs/03 §4.4` 特别标注过：Ollama 的 `num_ctx` 不设会有**静默截断**——长 chunk 被悄悄砍掉，不报错，只是检索精度莫名下降。`.env` 里已经给了 `OLLAMA_NUM_CTX=1024`，代码里调用时必须把它传进 `options`。
