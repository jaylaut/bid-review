## 四、你需要手动执行的事

```bash
cd review-engine

# 1) 装依赖。注意 uv add 会同时写 pyproject.toml 和 uv.lock

# 3) 探针（不需要 GPU、不需要下模型）
PYTHONPATH=src uv run python -c "
from pathlib import Path
from rag.offline.parsers import sample_pages, detect_route
p = Path('../data/raw/tenders/20260910_27302393/0-磋商文件定稿-龙胜罗汉果全产业链智慧平台.pdf')
pages = sample_pages(p, 10)
print('页数', len(pages), '每页字符', [len(x) for x in pages])
print(detect_route(pages, scanned_threshold=0.05))"

# 4) 单份解析
PYTHONPATH=src uv run python -c "
from pathlib import Path
from rag.offline.parsers import parse_with_mineru
md = parse_with_mineru(Path('../data/raw/tenders/20260910_27302393/0-磋商文件定稿-龙胜罗汉果全产业链智慧平台.pdf'),
                       work_dir=Path('../data/parsed/_mineru'), backend='mineru', timeout_s=900)
print(len(md)); print(md[:300])"
```

## 七、4.x 适配记录（2026-11-05 晚，实测）

装完 `mineru 4.1.7` 之后，原来的 CLI 实现整个作废，改了实现路线。这一节记录原因和实测数据，避免以后再走回头路。

### 7.1 为什么放弃 CLI

| 事实 | 来源 | 后果 |
| --- | --- | --- |
| 4.x 的 `mineru` 是 Typer 子命令（`parse`/`read`/`server`/…），没有 `-p 输入 -b 后端` | `mineru/cli/main.py` | 原 `build_command` 直接把文件路径当页码传，必错 |
| `basic`/`standard` 档要连本地 parse-server，否则报 `Local parse-server is disabled. Use --tier flash or --remote` | 实测 | CLI 路径必须先 `mineru server start`，多一个常驻进程要管 |
| `--pages` 默认只解析前 10 页 | `mineru/cli/commands/parse.py` | 不加 `--pages all` 会静默只解析前 10 页 |
| SDK 的 `mineru.parse()` 是纯本地实现（`MinerUParser` → `backend.analyze`） | `mineru/parser/mineru_parser.py` | 不依赖服务端，也不跟着 CLI 参数变 |

### 7.2 现在的实现

- `parsers/mineru.py`：`parse_with_mineru(source, *, backend, timeout_s, work_dir)`，起子进程调 worker，`subprocess.run(timeout=...)` 兜住卡死。
- `parsers/mineru_worker.py`（新增）：子进程入口，`python -m rag.offline.parsers.mineru_worker <源文件> <tier> <输出md>`。
- 后端 → 档位映射：`mineru → basic`（文本型，onnx 小模型）；`mineru-vlm → advanced`（扫描件，需 8 GB 显存 + Turing）。
- 子进程隔离的三个理由：SDK 没有超时；单份峰值几 GB；原生库（DirectML / pypdfium2）崩了不连坐主进程。

**坑（已踩，写进 `mineru_worker.py` 注释）**：Windows 上 multiprocessing 用 spawn，MinerU 内部的 PDF 渲染 worker 会重新 import 主模块。若把 `mineru.parse()` 写在模块顶层，渲染子进程会递归再跑一遍解析，报的是 `PDF render worker exited: 1`，真实原因却是"主模块被执行了两次"。所有入口必须放在 `if __name__ == "__main__":` 里。

### 7.3 实测数据（本机：i7-6700K / 32 GB / GTX 1050 Ti 4 GB，DirectML）

| 样本 | 页数 | 耗时 | 产物 | 速度 |
| --- | --- | --- | --- | --- |
| 磋商文件（前 10 页） | 10 | 17.4 s（推理 11.5 s） | 8,123 字符 / 24 标题 | 0.87 页/秒 |
| 附件清单（单页表格） | 1 | ~9 s | 4,148 字符 / 0 标题 | 表格类文档本来就没有标题，正常 |
| 招标文件（最大，15.6 MB） | 数百页 | 5 min 09 s | 369,096 字符 / 182 标题 | ≈1 页/秒 |

按 1 页/秒外推，剩余 51 份如果平均 100 页，约 1.5 小时；最坏情况（都是几百页的大标书）约 4 小时，一个晚上能跑完。

### 7.4 这次暴露的两个环境问题

1. **中断后会留下 Doclib 后台服务**：实测残留 4 个 `python -m mineru.doclib.app` 进程（含 2 个 multiprocessing 子进程）。重跑前建议检查：
   ```powershell
   Get-CimInstance Win32_Process -Filter "name='python.exe'" | Select-Object ProcessId, CommandLine
   taskkill /PID <PID> /T /F
   ```
2. **可用内存只有 8.4 GB**（总 32 GB，其余被 Docker / Ollama / 浏览器占着）。解析大文件前先停掉 Ollama，否则 DirectML 显存不够时会退到 shared memory，进一步吃内存。
