# A8 · 观测与评测闭环

上一份：[A7](A7-并发与缓存.md) · 工期：3 天（埋点本身从 A0 起就断续在写，这里收口）

## 解决什么

前七个阶段每次都说"跑一下 golden set 看涨没涨"。这个"跑一下"必须是一条命令——不然改三行代码，没人愿意花 40 分钟手动跑批，然后质量悄悄下滑，三个月后从 81% 掉到 70%，没人知道是哪次改坏的。

第二件事：线上出问题时回答"这个评分项为什么判错了"。靠跑批答不了，靠 trace。

## telemetry.py

```python
from opentelemetry import trace

tracer = trace.get_tracer("review-engine")

# 用法：循环里每个关键动作包一个 span
with tracer.start_as_current_span("agent.step") as span:
    span.set_attributes({
        "task_id": state.task_id,
        "item_id": state.item_id,
        "step": state.step,
        "tool_name": decision.tool_name or "final",
        "latency_ms": elapsed_ms,
        "dense_hits": n_dense,        # 两路各自召回多少。掉到 0 说明某一路坏了
        "sparse_hits": n_sparse,
        "rerank_top1": rerank_top1,   # 拒答阈值看的就是它
        "verdict": verdict.verdict if verdict else "",
        "confidence": verdict.confidence if verdict else -1,
        "terminated_by": state.terminated_by or "",
        # 【why】terminated_by 必填（docs/02 §五）："答完"和"步数用完"
        # 的可信度天差地别，不记就没法在报告里区分
        "degraded": degraded,         # none | cloud_rerank | no_rerank | local_llm
        "prompt_tokens": pt, "completion_tokens": ct, "cost_cny": cost,
        "model": model, "prompt_version": pv, "index_version": iv,
    })
```

字段清单是按"排查时你需要什么"倒推的：判定错了 → 看 verdict/confidence/rerank_top1；变慢了 → 看 latency_ms 分段；变贵了 → 看 tokens/cost；看不出来 → 看 degraded 是否走了降级。**少一个字段，排查时就多猜一轮。**

导出配 OTLP → Langfuse（自托管，8GB 机器换 Phoenix，两者埋点协议一致）。Langfuse 里按 `item_id` 搜，一眼看到这个评分项每一步问了什么、答了什么。

## eval_runner.py：一条命令

```bash
uv run python -m agent.eval_runner --golden eval/golden_set.jsonl \
    --out eval/reports/$(date +%F)-$(git rev-parse --short HEAD).json
```

```python
# 报告固定结构（eval_runner 的 compare() 依赖这个结构做 diff）：
{
  "meta": {"commit": "...", "date": "...", "golden_rows": 80, "model": "...", "prompt_version": "..."},
  "overall": {"accuracy": 0.81, "avg_steps": 3.2, "avg_cost_cny": 0.021, "p95_ms": 4100},
  "by_verdict": {"PASS": {...}, "PARTIAL": {...}, "FAIL": {...}, "NOT_FOUND": {...}},
  "retrieval": {"hit_at_5": 0.88, "recall_at_20": 0.93},
  "faithfulness": 0.87,
  "refusal": {"not_found_precision": 0.92, "not_found_miss_rate": 0.03},
  "hard_cases": {"cross_section": 0.74, "attachment": 0.71, "neg_deviation": 0.68},
  "termination": {"answer": 0.91, "max_steps": 0.06, "budget": 0.02, "timeout": 0.01}
}
```

hard_cases 单独跑：跨章节 / 附件类 / 负偏离三组各 30 题。**客户在意的是这 20% 难例**——它们才是人工成本的大头。总准确率涨 2 个点但难例没动，说明优化没落在刀刃上。

## compare()：自动对比

```python
# 用法：uv run python -m agent.eval_runner --base eval/reports/a.json --new eval/reports/b.json
# 输出每项指标的差值 + 方向判断（↑ / ↓ / ≈）

# 判定"退步"的规则（写死，不靠人感觉）：
GATES = {
    "overall.accuracy":        {"max_drop_pt": 0.5},   # 掉 0.5pt 以上 → 阻断
    "refusal.not_found_miss_rate": {"max_rise_pt": 1.0},  # 漏检涨 1pt → 阻断
    "overall.avg_cost_cny":    {"max_rise_pct": 15},       # 成本涨 15% → 阻断
}
# 【why】漏检率的门槛比总准确率严：漏检的代价是放走不合格方案，
# 业务上比"总体分低一点"贵得多。总指标变好、关键子指标变坏，按退步处理
```

## CI 门禁

```yaml
# .github/workflows/eval-gate.yml（或 GitLab CI 同理）
eval-gate:
  script:
    - uv run python -m agent.eval_runner --golden eval/golden_set.jsonl --out report.json
    - uv run python -m agent.eval_runner --base eval/reports/baseline.json --new report.json --gate
  # --gate 退出码非 0 = 阻断合并
```

门禁会拖慢合并（评测要 40 分钟），两个务实处理：

- 日常 PR 跑**快测集**（20 题抽样，5 分钟），主干合并前跑全量 80 题
- baseline.json 在每次主干合并后自动更新——门禁比的是"和上一个主干比"

## golden set 的分桶纪律

```text
golden_set.jsonl（80+ 题）
├── dev_bucket（60 题）—— 调参、调提示词随便用
└── holdout（20 题）  —— 只在主干合并/发版前跑，平时绝对不碰
```

> 【坑】在同一批题上反复调阈值和提示词，最后 92% 的分数是"背答案背出来的"，换一批题立刻回到 65%。holdout 从建集那天起就隔离，谁都不许看。A6 标定阈值时最容易犯这个错。

## 完成标准

- 一条命令出全量报告，文件名带日期 + commit
- eval_runner 的 compare() 对两份报告出 diff，三条门禁生效（人为制造一次退步，验证会阻断）
- Langfuse 能按 item_id 查完整轨迹，每个 span 字段齐全
- holdout 桶存在且从未被日常调参使用（git log 可查它只出现在发版提交里）

## 本阶段术语

> 【白话】**span**：trace 里的一小段（一次检索、一次 LLM 调用）。整条 trace 是很多 span 串成的调用链。
> 【白话】**回归**：新改动把原来对的题改错了。防它的唯一办法是每次改动自动跑全量。
> 【白话】**门禁**：分数不达标不许合并代码。机器拦，比人盯靠谱。
> 【白话】**holdout**：留出集。只在最后验收用的题，平时不看——看了就等于把它泄进了训练循环。
