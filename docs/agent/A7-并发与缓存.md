## 单项跑通 ≠ 任务跑通

80 项串行 40 分钟，用户等不了。但并发会同时撞上**三个容量差很远的瓶颈**：

| 资源 | 容量 | 是不是瓶颈 |
| --- | --- | --- |
| 云 LLM 配额 | 约 8 并发（RPM 限制） | 是，主要瓶颈 |
| Ollama 重排 | CPU 单实例，0.5–1.5s/对 × 20 候选 | **是，最容易被忽略的瓶颈** |
| PG 连接池 | 通常 20–50 | 视配置，容易被打爆 |

只限 LLM 并发、不管重排，是这一阶段最常见的错：8 个项同时进重排，Ollama 单实例排队，每项 30s 变成 8×30s 串行——表面上"LLM 并发 8"，实际总耗时被重排拖死。

## scheduler.py

```python
LLM_SEM = asyncio.Semaphore(settings.agent_llm_concurrency)      # 8
RERANK_SEM = asyncio.Semaphore(settings.agent_rerank_concurrency)  # 2

# 【why】两个信号量分开，分别包住对应的资源调用（在 models/ 层内部 acquire）：
# LLM_SEM 包 LLM HTTP 调用，RERANK_SEM 包重排调用。
# 不是"外面一个大信号量包整个评分项"——那样 8 个项同时各占一路资源，
# 两边都在排队，等于没限

async def review_all(items: list[ScoringItem], ctx: AuthContext) -> list[AgentState]:
    async def one(item: ScoringItem) -> AgentState:
        try:
            # ScoringItem → AgentState：item_text / requirement_must 落进 state
            # （A0 契约），此后查询构造、覆盖率、恢复全认 state，不认 item
            state = new_state(item)
            state = await run(state, ctx, llm, tools)
            return state
        except Exception as e:
            # 【坑】asyncio.gather 默认一个异常全体失败：
            # 1 个评分项炸掉，79 个已成功的结论全丢。
            # 必须逐项捕获，失败项记 failed + needs_human，其他人照常跑
            log.exception("item failed", item_id=item.item_id)
            return failed_state(item, e)

    return await asyncio.gather(*[one(i) for i in items])
```

失败项的状态是 `failed` 而不是让任务整体 `FAILED`：Java 侧拿到 `DONE_WITH_ERRORS`，报告照出，失败项进人工队列。**单点故障不扩散**是这个阶段最重要的设计约束。

## 连接池配置

```python
# PG_POOL_MAX = LLM 并发 × 4 + 8 = 40（.env 已配）
# 【why】系数 4：单步内并发持有多个连接——检索一个、checkpoint 写一个、
# 元数据查询一个，高峰再叠恢复逻辑。按"并发数"配池子（比如 8），
# 表现为"LLM 不慢，但一直等连接"，P95 上去还查不出原因，
# 排查时极易误判成模型慢。宁多勿少，连接是空闲复用的
```

asyncpg 连接的获取要短持有：查询完立刻还，绝不在 LLM 调用期间握着连接。review 代码里凡是 `async with db.acquire()` 后面跟 `await llm...` 的写法都是 bug。

## 缓存：省的是真钱

```python
# 三级缓存，键的设计决定命中率（docs/03 §六）

# L1：查询向量。同评分项重试、跨任务相同表述直接省一次嵌入调用
key1 = sha256(query_text)

# L2：检索结果。方案微调后重评，未变章节全命中
key2 = sha256(f"{item_id}|{doc_version}|{retrieve_params_hash}")
# 【why】键里必须有 doc_version：方案改了一页，缓存不失效的话
# 会拿旧内容判新方案——这是正确性 bug，不是性能问题

# L3：完整 Verdict。同一方案二次评审，token 成本≈0
key3 = sha256(f"{item_id}|{doc_version}|{prompt_version}")
# 【why】prompt_version 也要进键：提示词改了，旧判定不能复用，
# 否则提示词优化永远"看不见效果"（全被缓存挡住）

# 存 Redis，TTL：L1 24h / L2 168h / L3 按需（方案版本没变就长期有效）
```

L3 是商业价值最大的一层：客户改一页方案重新评审，79 项直接命中，只重算 1 项。成本从 ¥2 降到 ¥0.03，响应从 6 分钟到 30 秒。

## 压测

```python
# 压测脚本：同批题 × 3 个任务并发（240 项）
# 观察四个数：
#  1. 80 项总耗时：目标 6–8 分钟。超 10 分钟查分段耗时：
#     LLM 排队？重排排队？等连接？（trace 里每段都有 latency_ms）
#  2. 429 率：<1%。超了把 LLM_SEM 收小，别硬扛——
#     429 后重试虽然 tenacity 能兜，但重试本身就是放大流量
#  3. P95 单项耗时：比串行中位数劣化 <50%
#  4. 失败隔离：人为让 5% 项抛异常，其余 95% 必须正常出结论，
#     任务状态 DONE_WITH_ERRORS 而非 FAILED
```

压测报告落 `eval/reports/`，和准确率报告同等对待——面试里"我的压测数据是……"比"我做了压测"值钱得多。

## 完成标准

- 80 项 6–8 分钟（串行基线 40 分钟）
- 二次评审（同方案）LLM token 消耗 ≈0，端到端 30 秒内
- 5% 故障注入：95% 正常出结论，任务不整体失败
- 3 任务并发压测：429 <1%，P95 劣化 <50%
- 成本看板能看到单项/单步/单工具的 token 与钱

## 本阶段术语

> 【白话】**信号量**：食堂 8 个窗口，80 人排队，同时只有 8 个人在打饭。把并发压到下游配额以内。
> 【白话】**429**：API 说"请求太频繁，歇会儿"。硬扛重试是放大流量，正确做法是从源头（信号量）收紧。
> 【白话】**P95**：100 次里第 95 快的那次。比平均值更能反映用户体验——平均值会被大量快请求稀释。
> 【白话】**连接池**：提前建好一批数据库连接反复用。新建连接的耗时常常比查询本身还长。
> 【白话】**TTL**：缓存条目的保质期。过期自动清，防止用旧数据。
