上一份：[A2](A2-主循环.md) · 工期：4 天 · 前置：A2 循环已收敛（`answer` 占比 ≥85%）

## 四个工具对应评审员的四个动作

| 工具 | 评审员的动作 | A1 基线做不到的事 |
| --- | --- | --- |
| `search_in_bid` | 翻书找关键词 | 只能搜一次 |
| `get_section` | 翻到整节读完整上下文 | 只有 512 token 碎片，看不出"提了达梦没提金仓" |
| `check_required_doc` | 翻附件目录核对证明材料 | 完全看不到附件 |
| `compare_clause` | 逐字比对要求与应答 | 一次判 5 个要求，判得笼统 |

> **命名对齐**：02 §2.2 时序图里写的 `check_doc` / `compare` 是后两个工具的简写；
> 注册名以 `check_required_doc` / `compare_clause` 为准——01 §Phase3 与 02 §4.4 的
> 工具名单是权威，11 §P4 的记录同样用全名。简写只允许出现在叙述里；代码、prompt、
> 工具注册表里必须是全名——模型按名调工具，简写会让它调到一个不存在的工具。

每个工具都是**纯查询**（只读）。所有写操作都在 loop 里由代码控制——让模型决定写什么，重试一次就写两遍。

## registry.py

```python
TOOLS: dict[str, ToolSpec] = {}

def register(spec: ToolSpec):
    def deco(fn):
        assert spec.name not in TOOLS, f"工具重名: {spec.name}"
        # 【why】启动时炸好过运行时炸。重名说明复制粘贴忘改名字，
        # 模型会永远调到旧实现，且没有任何报错
        TOOLS[spec.name] = spec
        return fn
    return deco

# 启动自检：每个 spec 的 params 必须是 BaseModel 子类
def validate_registry():
    for s in TOOLS.values():
        assert issubclass(s.params, BaseModel)
        assert s.when_not_to_use, f"{s.name} 缺 when_not_to_use"
        # 【why】强制要求写"什么时候别用"。这是实测中降低误调率最有效的一行
```

## search_in_bid.py

```python
@register(ToolSpec(
    name="search_in_bid",
    description="在投标方案中检索与查询最相关的段落",
    params=SearchParams,
    when_to_use="首次查找某要求的应答位置；或换角度重查",
    when_not_to_use="已知章节号想读全文时（用 get_section）；查证明材料（用 check_required_doc）",
    cost_hint="1 次检索，约 200ms",
))
async def search_in_bid(args: SearchParams, ctx: AuthContext) -> ToolResult:
    # 直接复用 rag/online 的链路。【坑】不要在这里重写一遍检索：
    # 两套检索代码意味着评测数字和线上行为不一致，排查问题时两边互相甩锅
    hits = await retrieve(RetrieveQuery(
        query_text=args.query,
        keywords=args.must_terms or [],
        embedding=await embed_query(args.query),
        project_id=ctx.project_id,
        top_k=args.top_k,
    ), ctx)

    # 返回摘要不返回全文。【why】这是控制 token 的主闸门：
    # 模型看到摘要决定"要不要展开这一节"，全文用 get_section 取。
    # 80 项 × 6 步全回全文，单任务成本直接翻三倍
    summaries = [
        HitSummary(
            section_path=h.section_path, page=h.page_start,
            text=h.content[:300], score=h.rerank_score, chunk_id=h.chunk_id,
        ) for h in hits
    ]

    # coverage：must 里每条关键词是否在候选中出现。
    # 【why】这是给模型的"进度条"——它自己看到还缺什么，
    # 比你在 system prompt 里反复叮嘱"注意检查完整性"有效得多
    coverage = {term: any(term in h.content for h in hits) for term in (args.must_terms or [])}

    # next_hint：机械规则生成的下一步建议，不是 LLM 生成
    missing = [t for t, ok in coverage.items() if not ok]
    hint = f"未覆盖: {missing}，建议用这些词再搜或用 get_section 展开相关章节" if missing else "must 全覆盖，可出结论"

    return ToolResult(payload={"hits": summaries, "coverage": coverage, "next_hint": hint},
                      latency_ms=..., summary=f"{len(hits)} hits, coverage {sum(coverage.values())}/{len(coverage)}")
```

`coverage` 和 `next_hint` 是这个工具比"裸检索"强的地方。工具返回的职责不止给数据，还有**告诉模型下一步该干什么**——没有这个，模型就用几乎一样的词反复搜。

## get_section.py

```python
@register(ToolSpec(
    name="get_section",
    description="按章节号读取投标方案完整小节（父块，约 2000 token）",
    params=SectionParams,       # doc_id + section_path
    when_to_use="检索命中后需要完整上下文判断；碎片看不出完整含义时",
    when_not_to_use="只是想确认有没有提到某词（search 就够）",
    cost_hint="约 2000 token，1 次读库",
))
async def get_section(args: SectionParams, ctx: AuthContext) -> ToolResult:
    # 取父块不是子块。【why】这就是父子块设计的兑现口（docs/03 §4.3）：
    # "支持国产数据库适配"的应答分散在正文承诺 + 附件清单 + 实施计划三处，
    # 只看子块会漏判 PARTIAL，看整节才知道"提了达梦没提金仓"
    section = await fetch_parent_chunk(args.doc_id, args.section_path, ctx)

    return ToolResult(payload={
        "section_path": section.section_path,
        "page_start": section.page_start, "page_end": section.page_end,
        "content": section.parent_content,
        "subsections": section.child_paths,   # 子节标题列表：告诉模型还能往下钻
        "truncated": section.token_count > 2000,
        # 【why】truncated 必须显式说：模型对"内容被截断"毫无感知，
        # 不告诉它，它会把半截内容当完整内容下结论
    }, ...)
```

## check_required_doc.py

```python
@register(ToolSpec(
    name="check_required_doc",
    description="在附件/资质章节中查找评分项要求的证明材料",
    params=DocCheckParams,      # item_id + doc_types
    when_to_use="要求含'提供 XX 证书/报告/证明'类评分项",
    when_not_to_use="纯技术参数类要求（证据在正文里）",
    cost_hint="1 次检索，约 300ms",
))
async def check_required_doc(args: DocCheckParams, ctx) -> ToolResult:
    found, missing, ambiguous = [], [], []
    for dt in args.doc_types:
        hit = await search_in_scope(dt, scope=["附件", "证书", "资质", "目录"], ctx=ctx)
        if not hit:
            missing.append(dt)
        elif has_full_content(hit):
            found.append(DocRef(name=hit.title, page=hit.page))
        else:
            # 三态设计的核心：只有标题没有正文 → ambiguous，不算找到
            # 【why】投标方最常打的擦边球就是"附件目录里有条目、正文里没有内容"。
            # 二值化（找到/没找到）会把这类判成"找到"，ambiguous 单列，
            # 直接推高 needs_human，让人来定
            ambiguous.append(dt)
    return ToolResult(payload={"found": found, "missing": missing, "ambiguous": ambiguous}, ...)
```

## compare_clause.py

```python
@register(ToolSpec(
    name="compare_clause",
    description="把一条原子要求与一段候选原文逐字比对",
    params=ClauseParams,        # requirement: str, candidate_text: str
    when_to_use="must 拆出的单条要求与候选段精细比对；判定 FAIL/NEG_DEVIATION 前",
    when_not_to_use="批量判断（先 search 定位，再逐条 compare）",
    cost_hint="1 次短 LLM 调用，约 1s",
))
async def compare_clause(args: ClauseParams, ctx) -> ToolResult:
    # 单独一次 LLM 调用，temperature=0，短 prompt，只判这一条
    # 【why】不做成"一次判 5 条"：一次判多条时模型给笼统的"部分响应"
    # 然后编几个缺口。单条比对时注意力全在一条上，gap 描述具体得多。
    # 这是把"糊判"拆细的核心手段，也是多步 Agent 相对单轮最实在的收益之一
    verdict = await llm.complete(CLAUSE_PROMPT.format(requirement=args.requirement,
                                                      candidate=args.candidate_text))
    return ToolResult(payload=verdict, ...)
```

## mcp_server.py

```python
# 把四个工具挂成 MCP server，Java 侧（或未来任何客户端）可调同一套实现。
# 【why】选 MCP 不选私有协议：Python/Java 双侧复用，工具换实现时客户端零改动。
# 但注意：Agent 循环内部调用工具走的是直接函数调用（dispatch），
# 不绕 MCP 网络层——本进程内多一层 HTTP 纯属浪费延迟
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("bid-tools")

@mcp.tool()
async def search_in_bid(query: str, must_terms: list[str] | None = None, top_k: int = 5) -> dict:
    # MCP 入口做鉴权转换：外部调用必须带 project_id，映射成 AuthContext
    ctx = auth_from_request()
    return (await search_in_bid(SearchParams(...), ctx)).payload
```

## 验收

- 四工具 × 四类用例全绿
- **工具选错率 <10%**：人工抽 50 条 trace，统计"选的工具和正确工具不符"的比例。偏高就重写 `when_not_to_use`，这行字比 description 有效
- 跨章节专项：A1 基线在这类题通常 40–50%，A3 后应到 70%+。这是 `get_section` 的直接功劳，单独跑一组证明它
- MCP server 手动起一次，用 inspector 或 curl 调通 search_in_bid —— **此项尚未落地**（02 §4.4 目标形态；11 §P4 记录 A3 完成态为 registry.py 四件套，见上文"关于 mcp_server.py"）。落地前不计入验收，当前验收以前三项 + 选错率为准

## 本阶段术语

> 【白话】**父子块**：文档切小片（子块，约 512 字）用来被搜到，小片记住所属大节（父块，约 2000 字）。检索用小片（准），喂给模型判定用大节（上下文全）。`get_section` 取的就是父块。
> 【白话】**三态**：找到 / 没找到 / 疑似找到。二值判断会把"只有标题没内容"当成"找到了"，招投标里这恰好是投标方打擦边球的地方。
> 【白话】**MCP**：把工具标准化包装的协议，任何客户端都能按同一接口调用。相当于给工具发了张"通用插头"。
