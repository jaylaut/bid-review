# A1 · 单步基线

上一份：[A0](A0-契约与骨架.md) · 工期：2 天 · 前置：A0 完成 + `rag/online/` 检索链路可调 + golden set 已就位

## 先说清楚这阶段为什么存在

你要造的是"给 RAG 加了几步决策"的东西。那么**不加这几步决策时能打多少分**，必须先量出来，否则 A2 之后涨了 5 个点，你分不清是决策逻辑的功劳还是提示词改动的功劳。

所以这一阶段的产物是一个"笨 Agent"：只检索一次、只判定一次。它走的 schema、提示词、模型、检索参数，和 A2 **完全相同**，唯一区别是 A2 有多步。这样后面算增益才干净——这是评测里"控制变量"的最低要求，不是什么高深方法。

## golden set 格式

```jsonl
{"item_id": "S3.2.4", "item_text": "支持国产数据库（达梦、人大金仓）适配",
 "category": "技术参数",
 "requirement_must": ["达梦适配", "人大金仓适配"],
 "expected_verdict": "PARTIAL",
 "expected_missing": ["人大金仓适配"],
 "evidence_doc": "投标文件-技术部分.docx", "evidence_page": 87, "evidence_section": "3.2.4"}
```

字段说明：
- `expected_verdict`：人工判的。**四种值都要有足够样本**，尤其 NOT_FOUND——它是最容易出错的类别，也是业务上最要命的
- `evidence_page/section`：标准答案的证据位置，用来算 Hit@5
- 数量少于 80 就别往下走。20 道题差一道就是 5 个点，噪声比信号大，后面所有"提升 3pt"的结论都立不住

## query.py

```python
def build_query(state: AgentState, ctx: AuthContext) -> RetrieveQuery:
    # 【why】不用 LLM 改写查询（docs/03 §5.1 已论证）：
    # 评分项文本本身就是精确的检索意图，"支持国产数据库（达梦、人大金仓）适配"
    # 没有歧义、没有口语。让 LLM 改写引入两个问题：改写结果不稳定（评测没法归因）、
    # 多花 token。定向检索用确定性模板就对了。
    # 入参从 state 读（A0 契约的 item_text / requirement_must）：
    # 评分项内容随状态走，崩溃恢复后不需要重新加载评分项就能重构造查询
    must: list[str] = state.requirement_must

    # 评分项原文 + must 要点拼接。must 要点补进查询文本，
    # 是因为"支持国产数据库适配"这句话本身可能不带"金仓"俩字，
    # 不拼进去的话，写金仓的那一段靠向量也能召回，但排名会吃亏
    query_text = f"{state.item_text}。要求要点：{'；'.join(must)}" if must else state.item_text

    # must 的名词短语 + 型号/标准号正则（[A-Z]{2,}\d*、\d+\.\d+(\.\d+)? 等）
    # 【why】喂给稀疏路：向量对 "达梦DM8" 和 "达梦 DM8" 的区分远不如字面匹配。
    # 型号类评分项漏检，九成是稀疏路没拿到关键词
    keywords = extract_keywords(must)

    return RetrieveQuery(
        item_id=state.item_id,
        query_text=query_text,
        keywords=keywords,
        embedding=embed_provider.embed_query(query_text),   # 含查询侧指令，见 docs/03 §4.4
        project_id=ctx.project_id,   # 权限过滤第一闸，来自调用方上下文，不信 state.scratch
        top_k=5,
    )
```

## query.py · run_baseline()：只检索一次、只判定一次

```python
async def run_baseline(state: AgentState, ctx: AuthContext) -> AgentState:
    # 第 0 步：构造查询。确定性模板，零 token
    q = build_query(state, ctx)

    # 第 1 步：唯一一次检索。走 rag/online 的完整链路（双路+RRF+重排），
    # 和 A2 用的是同一个函数——变量控制就体现在这里
    hits = await retrieve(q, ctx)
    state.tool_records.append(ToolRecord(
        step=0, tool_name="search_in_bid",
        args_digest=digest(q.query_text), latency_ms=0,
        result_summary=f"{len(hits)} hits", ok=True))
    # 检索结果进会话池（A0 契约字段 session_hits，不是自造的 last_hits）：
    # A6 证据回查、下面的 Hit@5 都从这儿读
    # 【why】必须落 state 不落局部变量：校验发生在循环之后，
    # 崩溃/挂起恢复之后池子还得在
    state.session_hits = [
        {"chunk_id": h.chunk_id, "page": h.page_start,
         "section": h.section_path, "text": h.content}
        for h in hits
    ]
    state.step = 1

    # 第 2 步：一次判定。会话池全塞进去
    # 【坑】这里别做任何"聪明"的处理——不截断、不重排、不筛证据。
    # 基线越朴素，A2 的对比越有说服力
    state.verdict = await judge_one(state, state.session_hits)
    state.terminated_by = "answer"
    return state
```

## query.py · judge_one()：单次判定 prompt

```python
JUDGE_PROMPT = """你是招投标评审专家。判断投标方案是否响应以下评分要求。

【评分要求】{item_text}
【原子要求】{must_list}

【候选证据】
{evidence_blocks}
每条格式：[S{i}] 文档 第{page}页 {section}：
{content}

【判定标准】
- PASS：must 中每一条都有明确应答
- PARTIAL：部分应答
- FAIL：方案明确写了低于要求的内容（如要求 99.9%，方案写 99%）
- NOT_FOUND：候选证据中没有任何相关内容
- NEG_DEVIATION：主动承诺低于要求

【硬性要求】
- 每个 evidence 的 text 必须是候选证据原文的连续摘录，一字不改
- 不确定的判定给低 confidence
输出 JSON，严格按 schema。
"""
```

两处措辞是故意的，不是随手写的：
- **"原文的连续摘录，一字不改"**——模型有把原文改写得更通顺的习惯，改写过的"原文"过不了 A6 的证据回查。在 prompt 里就要求，能省掉大量校验失败重试
- **NOT_FOUND 的触发条件写得最具体**——基线阶段 NOT_FOUND 准确率通常最难看，先在 prompt 里把"什么算没找到"钉死

```python
async def judge_one(state: AgentState, session_hits: list[dict],
                    extra: str = "") -> Verdict:
    """单次判定：把会话池里的证据全塞进去，一次出结论。

    【why】判定逻辑全项目只有一份：A1 基线、A2 主循环的 final、
    A2 的强制收口（force_conclude）、A6 的证据校验重试都复用这个
    函数——评测跑出来的分数才等于业务真实水平，不存在"评测版判定"
    的偏差。extra 用于给模型带话（"证据不足" / "校验失败请修正"）。
    """
    evidence_blocks = "\n".join(
        f"[S{i + 1}] {h.get('section', '')} 第{h.get('page', '?')}页：\n{h.get('text', '')}"
        for i, h in enumerate(session_hits)
    ) or "（无可用证据）"
    prompt = JUDGE_PROMPT.format(
        item_text=state.item_text,
        must_list="；".join(state.requirement_must) or "（无拆解）",
        evidence_blocks=evidence_blocks,
    )
    if extra:
        prompt += f"\n\n【补充要求】{extra}"
    return await llm.chat_json(prompt, Verdict)
```

调用参数：`temperature=0`、JSON Schema 强约束、解析失败重试一次。`temperature=0` 是判定任务的底线，否则同一份标书两次评审结论不一致，用户直接失去信任。

## 跑批与混淆矩阵（入口是 A8 的 eval_runner.py）

```python
# 评测脚本的原则：判定逻辑和业务代码共享同一份（query.py 的 judge_one），
# 评测专属的只有"读题"和"对比答案"两个环节。
# 共享保证：评测跑出来的分数就是业务真实水平，不存在"评测版代码"的偏差。

async def eval_one(case: dict, engine) -> CaseResult:
    state = await engine.run_baseline(make_state_from_case(case), ctx=TEST_CTX)
    v = state.verdict

    # 维度一：判定对不对。直接比 verdict 枚举
    verdict_ok = v.verdict == case["expected_verdict"]

    # 维度二：检索对不对。标准答案的证据页码出现在 top5 里算命中
    # 【why】用 page 而不是文本比对：文本可能在解析时被切到相邻块，
    # 页码是稳定锚点。要更严格可以 page+section 双重匹配
    hit5 = case["evidence_page"] in {h["page"] for h in state.session_hits[:5]}

    return CaseResult(item_id=case["item_id"],
                      expected=case["expected_verdict"], actual=v.verdict,
                      verdict_ok=verdict_ok, hit5=hit5,
                      confidence=v.confidence, steps=state.step)


def confusion(results: list[CaseResult]) -> dict[tuple[str, str], int]:
    # 行 = 人工标注（expected），列 = AI 判定（actual）
    # 【why】混淆矩阵必须看，只看总准确率会漏掉致命问题：
    # 总分 62% 可能是 PASS 类 85% + NOT_FOUND 类 40% 凑出来的，
    # 而 NOT_FOUND 判错的方向恰好是业务上最贵的——漏判放走不合格方案，
    # 误判冤枉投标方。这两个方向要分开统计，混在一起等于没看
    m = defaultdict(int)
    for r in results:
        m[(r.expected, r.actual)] += 1
    return dict(m)
```

输出报告存 `eval/reports/YYYY-MM-DD-<commit>.json`。文件名带 commit hash，不然跑 20 次互相覆盖，想对比"上周那次改动"时找不到。

预期区间 45–60%（docs/01 §Phase1 的口径；10 §四 按"记录即可"放宽到 40–65%，两者都以 40% 为下限）。**低于 40% 别进 A2**——问题多半在检索链路或解析质量，不在 Agent，做多少步决策都救不回来。

## 本阶段术语

> 【白话】**基线**：改进前的数字。所有"提升 X 个点"都是相对它说的。
> 【白话】**Hit@5**：正确答案的证据在前 5 条检索结果里出现没有。衡量"找得到吗"。
> 【白话】**混淆矩阵**：一张"人工判成什么 × AI 判成什么"的交叉表。对角线是判对的，看非对角线哪个格子最大，就知道下一步修什么。
> 【白话】**控制变量**：对比实验里只准变一个东西。基线和 A2 之间，模型、提示词、检索参数全部锁死，只准变"决策步数"。
